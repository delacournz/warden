# @delacour/warden-e2e

warden's own mobile e2e stack (plan: `docs/plans/wdn-e2e.md`). No lease / build code here (that's `packages/core`); no CLI code (that's `apps/cli`, which imports from here).

## Publishing
Published as `@delacour/warden-e2e` (manifest from `apps/cli/src/npm/manifests.ts`, staged by `build:npm`) in lock-step with `@delacour/warden`; this `package.json` stays `private`.
- Public surface is `src/index.ts` (`.`) and `src/preload.ts` (`./preload`), bundled by `Bun.build` (`apps/cli/src/npm/e2e-bundle.ts`) into `index.mjs` / `preload.mjs` + one shared chunk: workspace packages inlined, `bun:test` and `zod` external. Everything else (`driver/*`, `env`, `runner/results`, ...) is workspace-private; `apps/cli` is compiled separately and imports it from the workspace, so it is deliberately not in the package `exports`.
- Declarations come from the TypeScript compiler API (`apps/cli/src/npm/declarations.ts`): `types/**` holds what the two entries reach, workspace imports rewritten to relative paths; `index.d.ts` / `preload.d.ts` re-export it. A type the public API exposes must be reachable from the entries. Consumers need `moduleResolution: bundler` (Bun's default) and `@types/bun`.
- A new third-party runtime import must be added to `E2E_EXTERNALS` and this package's `dependencies` (the bundle test fails on any bare import other than `zod`).

## Tracing (`runner/trace.ts`, `runner/span.ts`)
`trace.jsonl` holds `step-start` / `step-end` (what the console prints) and trace-only `span` lines `{type:"span", ts, op, ms, ok, code?, detail?}`: `ts` is when the call **started** (epoch ms), a span is written when it ends (so file order is not `ts` order), `ok:false` carries the error `code`.
- `op` names the layer: `driver.<call>` (every `Driver` call, incl. `driver.app.<call>` and optional capabilities; `driver/traced-driver.ts`, a `Proxy` that `session.driver()` returns), `device.<call>` (`traced-device.ts`, wired in `fixtures.ts`), `read.<call>` (`Locator` reads, detail `{locator}`).
- Code deep in a call leaves scalars for its span with `noteSpanDetail` / `addSpanDetail` (`driver/span-detail.ts`, an `AsyncLocalStorage`; a no-op outside a span): adb time/count (`adbMs`, `adbCalls`), the dump route (`dumpRoute`, `dumpRoutesTried`, `dumpMs`), settle `via`/`reason`. `session.span(op, fn, { detail?, verdict? })` is the same thing for any other call; it just runs `fn` outside an attempt.
- `Driver["settle"]` stays `{quiet, waitedMs}` (frozen contract); drivers answer the wider `SettleDetail` of `driver/settle.ts` (`via`: `stream | snapshot | hash`, `reason`, `frontmostPid`; iOS passes the helper's reply through; Android says `stream` when `warden-uiad` waited for the events to stop, `snapshot` when one dump covered `quietMs` and `hash` when it compared snapshots, and so does the iOS hash fallback (`hash`, which holds the screen still for at least `HASH_FALLBACK_MIN_QUIET_MS` = 500 ms whatever `quietMs` asks: a navigation push shows both screens for 300-460 ms); a late helper answer is `reason: "helper_timeout"`), `settleDetailOf` reads it back off the narrow type, and `device.settle()` returns it. Both settle spans carry it as `detail`.
- Spans are buffered (`SPAN_BUFFER_MAX`) and appended before the next step event or by `TraceWriter.flush()` when the attempt ends; no `appendFileSync` per RPC. Arguments are never recorded (`typeText` carries passwords).
- The bench's `untracedMs` per test (`packages/e2e-bench/src/adapters/parse/warden-results.ts`) is the test wall time that no step and no span covers; anything that shows up there is a call nobody wrapped.

## Rules
- Never run real `simctl` / `adb` / `warden-simd` in `bun test` — inject `Exec`, use `driver.testing.ts` / `native/scripts/fake-simd.ts`. Smoke scripts live in `native/scripts` and are run by hand.
- `Result` / `AsyncResult` from `@delacour/warden-types/result`; `DriverResult<T>` = `AsyncResult<T, DriverError>`.
- Import files directly (`@delacour/warden-e2e/driver/open`), no barrels except the published `src/index.ts`.
- Do not change `driver/driver.types.ts` or the `WARDEN_*` names in `env.ts` without updating `docs/plans/wdn-e2e.md` — other agents build on them.
- Tests colocated (`*.test.ts`), TDD, no `any`.

## Android driver internals (`src/driver/android`)
One resident `adb shell` per driver for `input`, `am`, `pm` and the dump fallback. With the server on (the default, below) snapshots, settle and input go to `warden-uiad`; without it every snapshot is a `uiautomator dump` (~1.9 s: JVM start plus its own `waitForIdle(1000, 10000)`).
- **`warden-uiad`, the resident UiAutomation server** (plan WDN-PERF, "Android server"): `native/android/src/**/*.java` (`Main`, `Uia`, `Json`), a ~27 KB dex run by `app_process` as the shell user over its own `adb shell` (`exec env CLASSPATH=/data/local/tmp/warden-uiad-<hash8>.dex app_process / nz.co.delacour.warden.uiad.Main`), NDJSON on stdio, protocol 1, one op at a time in order. A fresh snapshot takes ~6-30 ms (hierarchy of 40-190 nodes) against the dump's 1.9 s; a tap ~30 ms against ~330 ms; `settle` waits for accessibility events to stop (`via: "stream"`). Ops: `health`, `snapshot`, `settle`, `tap` (`count`, `holdMs`), `swipe` (`pressMs`/`releaseMs` make a drag), `gesture` (1-2 finger `paths`, `frameMs`, `holdMs`, `releaseMs`; server 0.3.0), `key` (`times`), `typeText` (insert at the caret, replacing the selection; unicode; `E_NO_ELEMENT` with no focus, `E_UNSUPPORTED` in a password field that has text), `selectAll`, `setText` (replace the focused input's text; the TS side is the optional `SetsText` capability in `driver/typing.ts`, used by `screen/field.ts` `focusClearType` for a fill over a plain field that holds text only when opted in (`ClearMethod` `"setText"` or `WARDEN_ANDROID_SETTEXT=1`; off by default because `Uia.setText` takes `root.findFocus` from the server's cache instead of re-reading focus like `typeText`/`selectAll` via `focusedInput()`, so it can hit the field focused before), read back like any fill; empty and secure fields are still typed), `a11yEvents` (`since` cursor; server 0.5.0; `A11yEvents.java` buffers `TYPE_ANNOUNCEMENT` and live-region text changes in a 200-entry ring, reply `{events:[{kind,text,at}],cursor,lost?}`; reached through the optional `ReadsA11yEvents` capability in `driver/a11y-events.ts`), `screenshot` (unused: `screencap` is as fast), `touch.down|move|up|cancel` (live touch, server 0.7.0, `LiveTouch.java`: `{x,y,pointer?=0}` in pixels; DOWN / POINTER_DOWN / MOVE (sync=false, every held finger) / POINTER_UP / UP (sync) / CANCEL on one down time per gesture, pointer ids 0-1; a move/up on a pointer that is not down or a second down is `E_BAD_REQUEST`; a watchdog thread lifts a finger with no down/move for 10 s; reply `{down, injectUs}`. TS: `uiad-ops.ts` `touch`: a state error or refusal is the answer and the server stays up, `E_BAD_REQUEST unknown op` (an older server, e.g. a host's) is `E_UNSUPPORTED` `detail.reason: "helper_outdated"`, remembered; no `input` fallback (it cannot hold a finger), so the driver offers `LiveTouch` only with the server option. Measured on an API 37 emulator (`native/scripts/touch-bench.ts`, warm): inject per move p50 0.36 / p95 0.70 ms, round trip over adb p50 1.8 ms, through the driver p50 2.1 / p95 3.6 ms; DOWN and UP take ~12 ms in the device's input dispatcher), `shutdown`.
  - **Files**: `uiad-protocol.ts` (wire schemas, `parseUiadNodes` input), `uiad-client.ts` (spawn, `ready` handshake, request ids and timeouts, a timed-out request kills the server), `uiad-device.ts` (dex path by hash, write through `adb shell cat`, launch argv, `ps` holder lookup, the busy rule), `uiad-backend.ts` (lazy single-flight start, restarts, give-up rules, `uiadUnsupported` in the state file), `uiad-ops.ts` (what the driver asks of it, and which failures fall back), `uiad.testing.ts` (in-process fake server that replays `fixtures/uiad-session.ndjson`), `uiad-dex.generated.ts` (the dex as base64; `UIAD_DEX`). `android-driver.ts` calls `uiad?.…() ?? <old way>` for each op.
  - **Off, or not used**: `WARDEN_ANDROID_UIAD=0`; no `uiad` option (`openDriver` sets it only when no `spawn` is injected, so a test never reaches a real adb); API < 26; a saved `uiadUnsupported` build id in the state file; `E_UNSUPPORTED` / `connect_failed` on start (saved), or two failed starts in a row, or more than 4 starts (not saved). The server is started on the first snapshot / settle / input, never on open. `capabilities.nativeSettle` and `unicodeText` are true while it is in use.
  - **`gesture`** (GES-3): `driver.pinch` / `rotate` / `gesture` build a `GesturePlan` (`driver/gesture-geometry.ts`; pinch/rotate radius = `DEFAULT_RADIUS` x screen scale in px) and the server replays it as one multi-pointer MotionEvent stream (DOWN, POINTER_DOWN, a MOVE per frame on an absolute schedule, POINTER_UP, UP; reply `{frames, pointers, maxLagMs, via}`). A refusal (`E_HID`, `E_UNSUPPORTED`) falls back: one finger becomes a `gestureMotionCommand` line (`input motionevent`, sdk 26+, at most 12 MOVEs), two fingers are `E_UNSUPPORTED` (`input` cannot do multi-touch). A failure after a finger went down sends CANCEL and is `E_INTERNAL`. Capabilities: server on `pinch:true, maxPointers:2`; off `pinch:false`, `maxPointers` 1 on sdk >= 26, else 0. Needs a device re-record of `fixtures/uiad-session.ndjson` (the gesture lines in `record.ts`) and a `native/android/scripts/smoke.ts` run.
  - **Fallback per call**: a refused op (`E_HID`, `E_NO_ELEMENT`, `E_UNSUPPORTED`) is done by `input` for that call; a dead or hung server is stopped first (a dump dies with `Killed` while any client holds UiAutomation) and a read (snapshot, settle, selectAll) falls back to the dump, while a tap / swipe / key / typed text is surfaced as the error, because it may have landed (a request that never left is sent again to a new server). A key with a modifier is still `input keycombination`.
  - **One UiAutomation client per device**: a second server answers `fatal` `E_AX_UNAVAILABLE` `detail.reason: "uiautomation_busy"`. `launchUiad` then lists holders (`ps -A -o PID,ARGS`): only `warden-uiad` processes and nothing else are killed (by pid) and the start retried once; anything else (`am instrument`, Maestro, a `uiautomator` run) is named in the error and left alone, and snapshot / settle return that error (the dump would only say `Killed`). Taps, keys and text still work through `input`. A busy slot is asked again after 2 s, never given up on, never saved.
  - **After text or a key** the ops wait for the accessibility events to stop (80 ms quiet): without it a press right behind `typeText` was lost 3 times in 20 on a React Native form, because the controlled input is still round-tripping through JS. The old `input text` took 300 ms to start and hid it.
  - **Build**: `bun run --cwd packages/e2e android:build` (`native/android/scripts/build.ts`: javac `-source 8` against android.jar, `d8 --min-api 26`; needs JDK 11+ and the SDK build-tools) writes `native/android/dist/`; **`bun run --cwd packages/e2e android:emit`** also regenerates `uiad-dex.generated.ts`. `uiad-dex.test.ts` fails when the Java changed and the module did not (it needs no toolchain), so any Java change is: edit, `android:emit`, re-record the fixtures when a reply changed (`bun native/android/scripts/record.ts --serial <leased emulator>` writes `src/driver/android/fixtures/uiad-session.ndjson` and `-busy.ndjson`, which `uiad.testing.ts` replays), and commit the Java, the generated module and the fixtures together. `native/android/scripts/smoke.ts --serial <serial>` is the on-device check (parity with the dump, tap, typeText, settle, busy refusal). The dex ships inside `@delacour/warden-e2e` and the `warden` binary as that base64 string (a test in `apps/cli/src/npm/e2e-bundle.test.ts` pins it).
  - **`warden-atf.jar`** (ATF audit engine, ~180 KB, built by `android:emit-atf`) is committed at `native/android/atf/warden-atf.jar` and is **never bundled**: inlined as base64 it held every `@delacour/warden-e2e` release in npm's automated review for ~16 min (`e2e-bundle.test.ts` fails on a base64 zip). `atf-dex.generated.ts` holds only its size and hashes; `atf-jar.ts` `loadAtfJar` takes `WARDEN_ATF_JAR`, else `$WARDEN_HOME/atf/warden-atf-<sha8>.jar`, else the committed file (workspace), else the `warden-atf-<sha8>.jar` asset of the version's GitHub release (staged by `build:npm`, uploaded before npm publish), sha256-checked. `ensureAtfJar` loads it only when the device lacks it; a failure is `E_IO` and the audit skips ATF.
  - Only API 37 (`google_apis_playstore_ps16k`, arm64) has been run on a device; API 26-36 are expected to work (reflection with fallbacks, see the plan) and fall back to the dump when they do not.
- **Settle** (server off, or it could not do this one) is one dump (`quiet` unless it failed or took ≥ 10 s) for any `quietMs` ≤ 1 s; only a longer window compares successive snapshots by hash. With the server it is the server's wait for the accessibility events to stop. `driver/settle.ts`'s `settleByHash` is shared with iOS's fallback and `warden ui`, so Android's shortcut lives in `android-driver.ts`.
- **Per-serial state** (`android-state.ts`): `$WARDEN_HOME/android/<serial>.json` = `{sdk, dumpRoute, animations}`, written atomically and best effort (an unreadable or hand-edited file reads as empty; values are validated before they reach a shell). It is trusted only on the API level it was written on. `openDriver` supplies the file store; tests pass `memoryAndroidState()`, never the real home.
- **Dump route**: the saved route is tried first; with none, `tty` first from API 30 (`routeOrder` in `android-dump.ts`), else `stdout`. A saved route that fails re-probes the others and the route that worked is saved. `warden ui` also keeps its own `android-dump-route` file and passes it as `dumpRoute` (wins over the saved one).
- **Animation scales**: open reads `window/transition/animator` scales and sets them to 0 in one shell call; the values to restore (`planAnimations`) are saved in the state file, and `close` puts them back. Right after zeroing, `transition_animation_scale` is put straight back to the device value (RN 0.86 reads it as reduce motion, so apps see it OFF by default; `a11y({ reduceMotion: true })` zeroes it, `false`/`null` restore `AnimationGuard.transitionOriginal()`, else 1.0) (an unset scale is `settings delete`d). A process that dies without closing leaves the originals in the file; the next driver on that emulator sees zeros plus saved originals and restores them on its close.
- **`openUrl`** is `am start -p <env.bundleId>`, so only the app under test can take a link.
- **Live stream** (`src/driver/android/stream/`, plan WDN-STRM STRM-2): `androidStreamService` answers `stream.start|keyframe|stats|stop` with the iOS helper's ranges, reply shapes and unit framing (`au-framing.ts`, `au-socket.ts`), served by `warden __android-host` (`serveDriver({stream})`, ready event `stream: true`). `source` `auto` (default) tries the emulator's gRPC bridge first: `warden-emud` (`native/ios` `Sources/warden-emud` + `WardenEmu`, staged beside `warden-simd`) calls `EmulatorController/streamScreenshot` over h2c with RGB888 frames in an mmap file, encodes them with the shared `WardenStream` VideoToolbox encoder (`emud.ts` spawns it, token in `WARDEN_EMU_GRPC_TOKEN`, never argv). Size = display long side capped at `maxEdge`; an odd side the emulator answers is encoded a pixel smaller. Else, and on every phone, `screenrecord.ts`: `adb exec-out screenrecord --output-format=h264` at half size, split into access units (idle drain), replaced by a second recorder before the 3 min cap and for every keyframe request, switching on its first IDR. Measured (Pixel 10 AVD, `-gpu host`, 2026-11-05): gRPC 56-58 fps at 570x1278 and ~56 at 1080x2424, `warden-emud` 0.07-0.15 core; software rendering (default) caps gRPC at ~15-20 fps and screenrecord at ~3-4.

## Reads after an input (`driver/observation-cache.ts`, `screen/context.ts`, `screen/locator.ts`)
Every read is a walk of the app's accessibility tree (helper CPU + runner parse). Measured on the bench suite (`.bench/snap-before`, this Mac, 2026-10-25): 183 snapshots + 41 hit-tests + 8 settles per rep; on the EAS worker (slower) 221 + 56.
- **Input generation** (`cacheObservations`): any non-read driver call moves the generation and notes `lastInputAt`; `settle` is a `WAITS` member: it drops the kept snapshot (it predates the wait) but is not input, and a `settle` that answers `quiet: true` clears `lastInputAt` (the app said the input landed), so `previous().sinceInputMs` is undefined after it and an action right after `app.open()` trusts one look.
- **The look right after an input is not wasted** (measured, do not "fix" it again): `driver.tap` returns once the HID press is over (~85 ms on a sim) and an AX read queues behind the app's main thread, so the `tap({ until })` check and the `expect` look taken 0–1 ms after a tap already show the screen the tap made on this Mac (first look passes). Holding the first check to `pollMs` and the first `expect` look to 100 ms saved 6 snapshots of 183 per rep and cost +7.7 s on a 53.6 s suite (`.bench/snap-after` vs `.bench/snap-before`), so it was reverted. On a slow host (EAS run `01a1739d`) that first look does miss, which is where the EAS trace's extra reads come from.
- **Stable-frame second look** (`actionableLook`): a look with no earlier one to compare against that comes within `STABLE_INPUT_GAP_MS` (300 ms) of an input is confirmed by `stillByHitTest` (one `elementAtPoint` at the element's tap point, `sameElement` as in `aimFromKept`) where `capabilities.cheapHitTest` and no `answerSystemAlert` (the app-scoped hit-test may not see a SpringBoard alert; the full look does), else by a second snapshot as before. A look that differs from the one before it never hit-tests.
- Changing any of these: `screen/observation.test.ts` ("a wait that starts right after an input", "a frame that held still across two looks"), `locator.tap-until.test.ts`, `observation-cache.test.ts` pin the counts and sleeps; the user-facing wording is in `apps/docs/content/docs/e2e/specs.mdx` ("Fewer snapshots", "Tap until something shows").

## `device.alert` and `device.openLink` (`src/device.ts`, `alert-reader.ts`, `device-link.ts`)
- `alert()` reads the alert ONCE through the bridge (`alertOn("axbridge")`: a screen without an alert is one tree read, no sleeps; the bridge sees what apps show themselves, e.g. the Keychain "Save Password?" sheet, and the permission prompts captured in `Fixtures`). A modal with no readable buttons yet (`{buttons:[]}`) is looked at again 3 times, 200 ms apart. A failed bridge read (it answers `E_APP_NOT_RESPONDING` for ~0.2 s after a launch, until a stream is bound to the new process: PERF-1.2) is followed by one host `ax` read; if that fails too the two-reader `driver.alert()` answers and retries transient failures (up to 13 reads, 100 ms apart). Measured on a sim: the first AX read after a launch costs ~200 ms whichever reader asks, then reads cost 6 to 40 ms; since `app.launch` waits for a bound stream (`rebind`, PERF-1.2) the gap after `app.open` is ~1 ms. Android has no `alertOn`: its `alert()` is one snapshot (`detectAlert` on it; ~10 ms from `warden-uiad`, a dump otherwise; the observation cache of PERF-2.1 reuses a fresh one).
- `openLink()` (iOS): reads alerts every 100 ms for 1 s, then every 250 ms (the poll that crosses the end of the quiet window is cut short to land on it); reads inside the first 1.2 s ask only the host `ax` reader (SpringBoard-hosted sheets, never slowed by the bridge), the first read after it asks both readers and is the confirmation that no sheet is up. A sheet is pressed only after it has been up for 500 ms (touches on a sheet that is still animating in are lost: observed on a fresh simulator, where three presses 120 ms apart all missed), at most 3 times, 600 ms apart, and the link is given up on 600 ms after the last press. Early return needs that confirmation AND `driver.isFrontmost(env.bundleId)` true. Why `frontmost` and not `settle{bundleId, quietMs:0}`: `settle` waits, can restart the stream and only reports the pid on a mismatch. While another app is in front (or the driver / bundle id cannot say) the full `waitMs` (8 s) applies. A link that returned this way is remembered per session and URL scheme (https: per host): later calls skip alert reads for 1.2 s and return once the app is in front. A sheet is not memoised. `until` (a `Locator`) returns when visible with no sheet up; `waitMs` caps everything and never throws. While it waits the session has a link in flight (`whileLinkInFlight` / `linkInFlight` in `device-link.ts`): `screenHostFor`'s `answerSystemAlert` answers nothing and `device.alert("accept" | "dismiss")` leaves an "Open in …?" sheet alone, so `lookForSheet` sees it and the scheme is not memoised as sheet-free; outside a link `"dismiss"` answers that sheet with Open, never Cancel.
- Limits to keep in mind: a sheet that shows later than 1.2 s while the app is already in front is missed (the old fixed 8 s window caught it); `waitMs` / `until` are the way to wait longer. A link whose bundle is not `WARDEN_BUNDLE_ID` never reports the app in front and keeps the full wait.

## `warden-simd` internals (`native/ios/Sources/warden-simd`)
NDJSON over stdio or a unix socket (`~/.warden/simd/<udid>.sock`, `warden e2e` passes it as `WARDEN_SIMD_SOCKET`). The wire is `src/driver/ios/simd-protocol.ts`; Swift output is pinned by goldens in `Tests/warden-simdTests/Fixtures` (`WARDEN_SIMD_UPDATE_GOLDEN=1 swift test` rewrites them, `native/scripts/element-shape.test.ts` parses them with the zod schemas).
- **Socket mode lifecycle** (`main.swift` `runSocket`, `Server/Announce.swift`, `Server/SocketServer.swift`): `--socket <path> [--idle-timeout <s>]` serves many clients; each connection still gets its own `ready` event. Once the socket is listening the process prints ONE process-level line on stdout, `{"event":"ready","socket":…,"pid":…,…identity fields}`, then, when stdout is a pipe or socket, `dup2`s stderr (the log file) onto fd 1, so a spawner that stops reading never blocks the helper and later events still reach the log. `warden` (`apps/cli/src/agent-ui/helper.ts` `watchStart`) reads that line instead of polling the socket file, connects once and hands that client to `openIosDriver({client})`; a helper without the line (older build; it only logs `listening on …`, which counts too) or a slow start falls back to the 100 ms poll. The line never waits for the quiescence stream: `Task { session.warmQuiescence() }` opens it in the background, and the first `settle` / relaunched read waits for it (`readRecovering` copes with it being absent). **Idle exit**: `--idle-timeout` (default 600 s, `0` = never) ends the process after that long with no client connected and no op in flight (`IdleTracker`, tested with an injected clock); `warden` passes 10 min, or `$WARDEN_SIMD_IDLE_TIMEOUT`. **Resident after release**: `warden` does not stop the helper when a lease is released, so the next run on the device reuses it; it is stopped by `release --shutdown`, `ui close`, a device shutdown, and replaced when the helper binary or its `WARDEN_SIMD_*` env changed, never because the lease owner changed (record in `$WARDEN_HOME/ui/<udid>/state.json`). One helper per sim still holds: a resident helper keeps its quiescence stream open until it exits, so anything else that opens a stream on that sim (another tool, a helper under a different `WARDEN_HOME`) stalls it and the other way round; the bench harness stops the helper before other frameworks run.
- **AX guests**: `Session.open` builds one `.exclusive` `axbridge` reader (a guest private to this helper, `automationMode: true`) plus a host `ax` reader for per-request fallback. A bridge failure with no explicit `backend` is retried on `ax`, with a `log` warn and `snapshot.fallback.reason`. A bridge answer of one childless area-less root is re-read once, then read on `ax` (`Session.recoverFromEmptyRoot`). **Silent guest** (`Device/BridgeStall.swift`, `Session.readAX`): each bridge read attempt is bounded by `WARDEN_SIMD_BRIDGE_DEADLINE_MS` (default 4000, `0` off; cold reads too); **cold guest** (`BridgeWarmth`): from helper start, a guest recycle/reap (`markCold`) or a `launch` until one bridge read answers, reads get `WARDEN_SIMD_BRIDGE_COLD_DEADLINE_MS` (default 12000, never below the warm one) and the first stall per cold spell does not arm the cooldown (a second does). `Session.warmBridge` starts a single-flight background read at helper start and after `rebind`; a read that arrives meanwhile waits for it, and goes to `ax` without its own bridge wait when it stalled. The TS driver sends `minTimeoutMs` = cold deadline + 8 s (`coldReadTimeoutMs`) on `snapshot` / `elementAtPoint` / `alertButtons` until a snapshot comes back from `axbridge` without a fallback on this helper generation, and again after each `app.launch`; a stall (`BridgeStalled`, wire `E_TIMEOUT` `detail.stage: "axbridge"` on an explicit `backend:"axbridge"`) or idb's `guestNotAnswering` is a bridge failure, so the read falls back to `ax`, and reads skip the bridge for `WARDEN_SIMD_BRIDGE_COOLDOWN_S` (default 20). **Recovery probe** (`BridgeProbe`, `Session.bridgeRecovery`): a read the cooldown (or a stalled warm-up) sends to `ax` starts a detached, single-flight probe (one `hitTest` at the screen centre, `BridgeProbe.defaultDeadlineMs` 1500, or the cold deadline while the guest is cold; at most every `defaultIntervalSeconds` 5, doubled per silent probe in a row up to `maxIntervalSeconds` 30) and does not wait for it; an answer clears the cooldown and the hold, warms the guest and clears `health`; a silent probe does not restart the cooldown but holds reads on `ax` until a probe answers (`BridgeStallGate.holdForProbe`) and marks the guest cold, so no caller pays the 4 s read deadline while the guest stays silent. **Stalled guest** (`BridgeReaper`, `Session.noteStall`): measured on a sim (SIGSTOPped guest), the guest serialises reads (5 concurrent reads end ~32 ms apart), cancelling a read ends its Swift await within ~100 ms even on a stopped guest and idb then ends that guest, so the next request starts a new one, cold (~0.4 s locally, seconds on a slow host); a read in flight when its guest is killed completes on a respawned guest. So a stall (past the deadline, not the cold exempt one) on a guest that had answered marks it cold and recycles it in the background (`GuestRecycling.endStalledGuests`: every guest of the sim, the stream reopened), at most `BridgeReaper.defaultMaxRecycles` 3 per helper (`WARDEN_SIMD_BRIDGE_MAX_RECYCLES`, `0` = never, invalid = default + warn at start; one that found no guest is not counted; then logged once; reported as `recycles` / `recyclesExhausted` in the stall report). The recycled guest gets the full cold rules of a fresh one: cold deadline, an exempt first stall, and `Session.warmBridge` once the recycle is over (`BridgeReaper` `rewarm`; single-flight); a warm-up that answers clears the gate and health, ending the cooldown the stall armed. While that warm-up is still reading, a read that would start a probe joins it instead (`BridgeWarmth.running`; the guest serialises reads, so a probe beside it would only queue a second cold read). A guest that is not recycled (budget spent, no reaper) gets no exempt stall. A cold guest is never recycled (that loops), so the budget bounds stall → recycle → cold cycles. Measured: stall → recycle 240 ms → cold probe answered 421 ms → reads back on `axbridge` ~1.5 s after the stall. An explicit `backend:"axbridge"` read inside the cooldown waits for that probe only, then reads, or fails as a stall (`E_TIMEOUT`) without a tree read (inside the probe back-off: at once). The TS screen layer does not re-read a fallback look itself (`Snapshot.fellBackFrom` is informational): the next poll reads the device and finds the bridge back. `alertButtons`' bridge half is bounded the same way and starts the probe when the cooldown skips it. Seen on GitHub-hosted `macos-26` runners (3 vCPU / 7 GB): every `snapshot` `E_TIMEOUT` at the client's 10 s, every launch `rebind: "timeout"`. Not the toolchain: the Xcode 27.1-built helper reads fine there on plain, golden and slim sims (85-800 ms warm), but a cold sim or one booted beside a local Xcode build answers its first bridge read in 4-11 s, idb's own query timeout equals the client's 10 s, and reads the client gave up on keep running in the helper. `app.launch` gives `rebind` 10 s (`REBIND_TIMEOUT_MS`; it answers as soon as it binds: 2.4-4 s warm, 8.6-11.3 s cold on that runner). The TS driver puts `backend` (always) / `fallback` on the `driver.snapshot` span. **Stall report** (`BridgeStallReport`, `Session.readAX`): every fallback carries `fallback.stall` and a failed read `detail.stall` (`{stage: connect|read|warm-up|cooldown, readMs?, deadlineMs?, guestAgeMs?, cold, cooldownRemainingMs?, probes, recycles, recyclesExhausted}`; `probes` = `BridgeStallGate.failuresInARow`, failed bridge reads and silent/failed recovery probes since the last answer; an explicit read failed by the probe is stage `cooldown` with the probe deadline, guest age from `WedgeWatch`, so a recycle resets it; `recycles` / `recyclesExhausted` = `BridgeReaper.recycles` / `exhausted` before this read, also in `health` as `bridgeRecycles {count, exhausted}` once one ran); `driver/bridge-stall.ts` parses it onto `Snapshot.bridgeStall` and the span (`stall*` fields), `runner/bridge-evidence.ts` sums an attempt's spans into `results.jsonl` `bridge {fallbacks, first, last}`, and `screen-at-failure.txt` gets a `# read on ax: …` line 2.
- **Wedged accessibility service** (`Device/AXWedge.swift`, `AXWedgeRecovery`): on a fresh iOS 27 sim (CI ~15%) backboardd's AX notification server can stop answering on first use; every AX client then blocks for the life of the boot (both readers time out), and only restarting backboardd clears it (ending guests or SpringBoard does not). Marker in the sim log: `Could not auto-register for pid status change`, but it is also logged by sims that still answer, so it never acts alone. `Session.readAX`: a read whose bridge was silent (stall, cooldown, stalled warm-up, idb `guestNotAnswering`) AND whose host read failed `serviceNotAnswering` calls `suspect()` (stall report `axWedge: "checking"`): a background, single-flight check: `simctl spawn log show --last 5m` for the marker → one host hit-test that must still time out (`livenessReadMs` 4000) → `launchctl kickstart -k user/foreground/com.apple.backboardd` → wait (≤15 s) for a SpringBoard pid that was not there before (`ps`, `GuestReaper.children`) → `afterBackboarddRestart` (end guests, `forgetAll` pids, `markCold`, clear the gate and health, reopen the stream, `warmBridge`). Budget `WARDEN_SIMD_AX_WEDGE_RESTARTS` (default 1, `0` never; only restarts count); a `not-wedged` verdict is not re-checked for 60 s unless forced. A read while it runs waits ≤5 s (`waitWhileRecoveringMs`), then fails `E_TIMEOUT` `detail.reason: "ax_wedge_recovering"` (not `E_AX_UNAVAILABLE`: two of those make the TS driver restart the helper). After a restart fallback reports carry `axWedgeRestarts`. `health.axWedge` / op `axWedge{recover?}` → `{restarts, maxRestarts, recovering, checked?, last?: {outcome restarted|not-wedged|failed, agoMs, ms?, error?}}`; `recover:true` forces a check and answers with `checked` (absent when the budget is spent). TS: `driver/ax-wedge.ts` (`RecoversAxWedge`, iOS driver `axWedge`, old helper → `E_UNSUPPORTED` `helper_outdated`); `Session.recoverAxWedge` reruns a failed attempt once per restart that happened during it (waits ≤60 s for one in flight); `apps/cli` warm-up `recoverInHelper` asks the helper first and only kickstarts itself for an old helper.
- **Unresolved frontmost** (`Device/FrontmostRescue.swift`, `Session.readTargeted`): both readers resolve `frontmost` through the same in-sim `AXPTranslator frontmostApplicationWithDisplayId:` (the guest's `windowServer` strategy, the host translator's `frontmost` request), so the `ax` fallback is not independent of it. On GitHub-hosted `macos-26` runners it answered nothing for minutes (`window-server frontmost returned no application`, host `did not answer a frontmost request within 5.0s`, later `named no frontmost application`) while the app drew fine. A snapshot whose frontmost cannot be resolved (`isFrontmostUnresolved`: bridge `frontmostUnresolved`, host `serviceNotAnswering(.request("frontmost"))` / `noTranslationObject(.frontmost)`) is read again as `.application(pid:)` for each of `frontmostCandidates()`: the pid `launch` last started (`BundlePidMemory.lastLaunched`, cleared by `terminate`), the stream's pid, then SpringBoard (one launchd lookup, only when nothing else is known). Reads then go straight to the pid for `WARDEN_SIMD_FRONTMOST_COOLDOWN_S` (default 20, `0` off; doubled per failure in a row, capped at 300 s: each probe costs a bridge stall plus a host timeout, ~7.6 s on the runner) and probe frontmost again after it. Measured on a hosted `macos-26` runner (diag run 42014333250, Settings app, golden clone built under CPU load): the 0.9.0 helper failed every snapshot (`did not answer a frontmost request`, then `named no frontmost application`, still 3 min later); this build read the first snapshot in 7.7 s by pid and every later one in 55-110 ms on the bridge (165 nodes); `running-board` made the bridge's own frontmost read work (0.8 s), only the host `ax` frontmost stayed dead. So the window-server frontmost lookup is what is broken there. The reply carries `target {pid, source}` and a `fallback` reason; the span `targetPid` / `targetSource`. `WARDEN_SIMD_FRONTMOST_METHOD` (`window-server` default, `running-board`, `center-point`; camelCase accepted) sets the guest's strategy. When both readers fail, `AXReadersFailed` keeps the bridge's reason (`detail.bridgeError`) next to the host error (`detail.axError`); host translator errors map to `E_TIMEOUT` (silent service, retryable) / `E_AX_UNAVAILABLE` with `detail.reason: "frontmost_unresolved"`, not `E_INTERNAL`. A failed `driver.snapshot` span notes `axStage` / `axReason` / `axRequest` / `bridgeError` / `axError`, and once per failure streak the helper's `health` (`bridge`, `bridgeLastError`, `hostXcode`, `helperXcode` from `builtWith` = the helper's `manifest.json`, `coreSimulator`). Not covered: the quiescence stream and `alertButtons` still read `.frontmost` (`rebind` times out). On a hosted `xcode-27` runner the native `settle` then fails with `E_AX_UNAVAILABLE` (`AXObserverAddNotification(4002) failed with AX error -25204 (kAXErrorCannotComplete)`) while snapshots read fine by pid: the TS driver polls snapshot hashes for that settle (span `nativeError: "E_AX_UNAVAILABLE"`, `via: "hash"`), and after two in a row stops asking the helper for the session (one log line). A native settle that works in between resets the count.
- **Quiescence stream** (`Ops/Settle.swift`, `QuiescenceMonitor`): one stream opened at helper start and kept for its life (the guest follows the frontmost app; ~0.5 s to open). `WARDEN_SIMD_STREAM_IDLE_S=<s>` closes it after that long without a `settle` (default off). Every stream spawns its own guest and two streams on one simulator leave each other stuck: one helper per leased sim. Measured with a second helper process on the same sim: reads stay correct in both, but `settle` falls back to snapshot stability (`via:"snapshot"`, ~2.5 s instead of ~260 ms) for as long as the other stream is open. Remedy: stop the stale helper (`warden ui close --udid <udid>`, or kill the `warden-simd --udid <udid>` process); `WARDEN_SIMD_STREAM_IDLE_S=1` on every helper only softens it (settles then reopen the stream, ~0.9 s, and still collide with a concurrently active one).
- **Wedged guest** (measured on device, PERF-0.4): about 22-26 s after a guest starts (idle or not, relaunches or not) it can answer every quiescence query with `busy(runLoopIdle, animationsInactive)` for every process, SpringBoard included, through any number of stream restarts and a replaced reader object; only ending the guest process clears it. Reads are unaffected, so `settle` falls back to `via:"snapshot"` (~1.0-1.3 s) until it is cleared. `Session.reapWedgedGuests` (`WedgePolicy`, `GuestReaper`): after a `snapshot` settle on guests that already gave a `stream` quiet verdict (and not within 5 s of the last reap) it ends every `SimulatorFrameworkBridge-iOS serve` child of this simulator's `launchd_sim` (found with `ps`; never another simulator's) and restarts the stream; idb respawns the reader's guest on the next read. Logged at `info`: `ended N AX guest(s) (reap K)`. A fresh guest that falls back on its first settle is just a busy app and is left alone. The reap is the backstop: `rebind` recycles guests before they wedge (`RebindPrelude`, `WedgeWatch.guestAge`): when the guests are at least `WARDEN_SIMD_GUEST_MAX_AGE_S` old (default 12, `0` = never) and it is not within 5 s of a reap, it ends them and restarts the stream before waiting for the bind (+~0.5 s on that launch, against ~1 s for the wedged settle plus ~0.45 s on the next read and settle). 12 s is tuned to ~8 s between launches (guests wedge from ~21 s): 18 s left 1-2 wedged settles per 8 tests, 12 s none, recycling off 3 of 8. Cost per wedge: that one slow settle plus ~0.3 s on the next read and ~0.25 s extra on the next settle.
- **Relaunch repair**: the stream follows a relaunch by itself (`targetChanged` then a state, ~0.6-0.8 s after `simctl launch`), but a read made before that fails `E_APP_NOT_RESPONDING`. `rebind{bundleId, rebindTimeoutMs?}` (below) is what `driver.app.launch` asks for right after `simctl launch`, so the first read finds the stream bound (first read ~25-90 ms; unrepaired it was ~1.5 s). If a read still fails, `Session.readRecovering` calls `recoverBridge(pid:)` with the pid the error names: `QuiescenceMonitor.recover(pid:)` waits up to 900 ms (`recoverFollowMs`) for the stream to report on that pid and restarts it only if it does not, waits for the first state (max 4 s), and the read is retried once, then falls back to `ax`.
- **Stream restarts are awaited**: `QuiescenceMonitor.restart()` cancels the old task and awaits it before requesting the next stream (the old task may still be inside its open call), so there are never two streams of this helper; concurrent restarts leave one. `waitQuiet` / `bind` re-read the stream's state, pid and clock after the launchd pid lookup (150-350 ms under load), so a stream that followed the relaunch during the lookup is not restarted.
- **`gesture` op** (`Ops/Input.swift`, `HIDPlan.gesture`): `{paths:[[{x,y}]] (1-2 equal-length arrays, 1-1000 points), frameMs=16, holdMs=0, releaseMs=0, unit?}` replays frame by frame as one gated composite (1 path = `touch` downs, 2 = `twoFingerTouch`, lifting together; one frame = a tap); `(N-1)*frameMs+holdMs+releaseMs` over 60 s is `E_BAD_REQUEST`. The TS driver (`rotate`, `gesture`) plans via `gesture-geometry.ts`. A helper built before this op replies `E_BAD_REQUEST unknown input op`: the driver maps it to `E_UNSUPPORTED` `detail.reason: "helper_outdated"` (restart with `warden ui close --udid <udid>` or `native:build`) and then fails fast without sending. `pinch` stays a separate op (`angle` in degrees).
- **Alerts / modal** (`Ops/Snapshot.swift`, `Session.topmostModal`): `alertButtons` and `snapshot.modal` pick the best container that holds a button, ranked alert/dialog (`Alert`, `_UIAlertController*` e.g. the Keychain "Save Password?" sheet, Safari `SFDialogView`, idb's named modal) > sheet > popover; ties go to the last in tree order. A tip popover never hides a dialog under it. App-owned prompts (Keychain, app alerts) are only visible on `axbridge`; `ax` reads such an app as one empty root. Debug params on `snapshot`: `raw:true` returns idb's document (source of `Fixtures/*.document.json`), `pid:<n>` reads that process instead of the frontmost app (SpringBoard pid: `xcrun simctl spawn <udid> launchctl list | grep SpringBoard`).
- **`alertButtons{backend?}`** (`Ops/Snapshot.swift`, `Session.answerAlert`): no `backend` reads both readers (`ax`, then `axbridge`: two tree reads when there is no alert). `backend:"ax"` or `"axbridge"` reads that reader only (one read; its failure fails the op). An `axbridge` read that finds idb's blocking modal but no container with a button answers `{buttons:[]}` (not `null`), so a caller can look again; the default read still answers `null` there. The TS side is `driver.alertOn(backend)` (`driver/alerts.ts`); `driver.alert()` stays the two-reader read.
- **`frontmost{bundleId}`** (`Ops/Snapshot.swift`) → `{frontmost, pid?, frontmostPid?}`: whether the bundle's launchd pid is the pid the quiescence stream last reported. The launchd lookup costs ~150 ms, so the pid is remembered per bundle (`BundlePidMemory`): while the stream's frontmost pid is the remembered one and `kill(pid, 0)` says it still runs, the answer is a comparison (a dead pid, i.e. a stream stuck on a relaunched app, forces the lookup). No tree read and no wait, unlike `settle{bundleId}` it never restarts the stream or judges quiet. `frontmost:false` with no `frontmostPid` = no stream state yet (the op opens the stream). Needs the bridge (`E_UNSUPPORTED` otherwise, an old helper answers `E_BAD_REQUEST`); callers treat any failure as "cannot tell". The TS side is `driver.isFrontmost(bundleId)`.
- **`launch{bundleId, args?, env?, terminateRunning?=true}` → `{pid}`, `terminate{bundleId}` → `{terminated}`, `openUrl{url}` → `{}`** (`Ops/App.swift`): app lifecycle in the helper's own process, which already holds CoreSimulator; the driver used to spawn one `xcrun simctl` per `app.open` / `openUrl`, each loading CoreSimulator again (0.12-0.16 CPU-s on the host, ~1.2 CPU-s and ~40 % of warden's host CPU per bench rep, mostly booked to the spec process as an exit charge). `args` follow the executable, `env` reaches the app as given (no `SIMCTL_CHILD_` prefix), `terminateRunning: true` ends a running instance first and `false` brings it to the front (its pid is answered); `launch` remembers the new pid for `frontmost` (`BundlePidMemory`). `terminated: false` = nothing was running (launchd has no job, or the kill failed and a lookup finds no process), not an error. Errors keep their meaning: a missing app is `E_APP_UNAVAILABLE`, a URL nothing handles `E_IO`, a URL without a scheme `E_BAD_REQUEST`. TS side: `ios-driver.ts` `app.launch` / `terminate` / `openUrl` ask the helper first (`launch` timeout 30 s, the others 15 s); `E_UNSUPPORTED` or the dispatcher's `E_BAD_REQUEST unknown op` (a helper built before these ops) is remembered and `simctl.ts` does app lifecycle for the rest of the session (logged once, `reason: "helper_outdated"` on that span). The launch span carries `via` (`simd` | `simctl`) and `pid`, the terminate span `via` and `terminated`. `install` / `uninstall` / `isInstalled` / `isRunning` / `clearData` stay on `simctl`. `native/scripts/smoke.ts` `lifecycleLeg` proves args + env (`launchctl procinfo`), relaunch vs keep-running (pid), terminate twice and a link of the app's scheme (`--scheme`). Goldens: `Fixtures/launch.reply.golden.json`, `terminate.reply.golden.json`.
- **`settle{quietMs=250, settleTimeoutMs|timeoutMs=3000, bundleId?}`** replies `{quiet, waitedMs, via, reason?, frontmostPid?}`. `via` is `stream` (guest reported run-loop idle + animations inactive for `quietMs`) or `snapshot` (stream stuck: restarted after 400 ms of `busy`, then two identical reads at least 500 ms apart (`FrameStability.minQuietMs`: a navigation push shows both screens at their final frames for 300-460 ms) once 700 ms have passed; see Wedged guest). `settleTimeoutMs` wins over `timeoutMs`. `bundleId` holds `quiet` back until the stream's frontmost pid is that bundle's process (`FrontmostGate`, timings in `FrontmostGate.Timing`; the pid is re-resolved every 150 ms, and the stream is restarted only once the bundle has a pid the stream does not report, 900 ms after it appeared (a healthy stream follows in 0.25-0.4 s; restarting sooner is slower and churns guests), then every 1.5 s, never while it is still opening or opened under 500 ms ago without a pid yet); at the deadline `quiet:false, reason:"frontmost_mismatch"`. A deadline is not an error. Needs `axbridge` (`E_UNSUPPORTED` otherwise; the TS side then polls hashes).
- **`rebind{bundleId, rebindTimeoutMs|timeoutMs=4000}`** (`Ops/Settle.swift`, `QuiescenceMonitor.bind`) replies `{bound, waitedMs, restarts, pid?, reason?}`: waits until the quiescence stream has reported a state for the bundle's own process (the pid is looked up again every 150 ms until it exists), restarting the stream only if it still reports another process 900 ms after the pid appeared. `bound:false` at the deadline is an answer (`reason`: `no_process`, `timeout`, `cancelled`), not an error. `recycled:true` says the helper first ended its aged AX guests (see Wedged guest); the wait budget includes that. Self-timed like `settle` (`Dispatcher.selfTimedOps`). `E_UNSUPPORTED` without the bridge, `E_BAD_REQUEST` from a helper that predates it; the TS side (`driver.app.launch` in `ios-driver.ts`) is best effort: any failure leaves the launch as it was (and these two are remembered, not asked again), `bound:true` clears the launched-bundle gate of the next `settle`, and the span carries `rebind`, `rebindMs`, `rebindRestarts`, `rebindRecycled`. It forgets the bundle's remembered pid (`BundlePidMemory`) first and its pid lookups remember the new process, so `frontmost` never answers from the pre-launch pid. Not a `Driver` capability (frozen contract): `launch` does it internally.
- **`stream.start{fps=60, bitrate=4000000, maxEdge=1280, keepaliveMs=1000, path?}` → `{path, width, height, fps, bitrate, framing}`, `stream.keyframe`, `stream.stats`, `stream.stop` → `{stopped}`** (`Ops/Stream.swift`, `Stream/*`; plan WDN-STRM STRM-1): live H.264 of the main display on a unix socket (default `$TMPDIR/wsimd-<udid8>.sock`, mode 0600, one reader; a newer connection replaces the older). Framing per unit: `u32 length, u8 flags (1 key, 2 config), u64 pts_us`, then Annex-B, big-endian (`AUFraming`). Own VideoToolbox session (`StreamEncoder`), not idb's video stream: idb's encoder ticks at a fixed rate and cannot be gated without breaking H.264 references, and it emits High profile, which browser peers do not negotiate. Constrained Baseline, real-time, no reordering, low-latency rate control; each frame is first copied (scaled to `maxEdge`, even sides, 0 = device pixels) into a pooled NV12 buffer, so the simulator drawing mid-encode never tears it. Damage-driven (`FramePacer`): a frame only after `.frameRendered` (`framebuffer.attach()` events; the `Framebuffer` must stay referenced or the events stop), capped at `fps` with renders in between coalesced, plus one keepalive per `keepaliveMs` on a still screen. A keyframe on start, on `stream.keyframe`, on a new reader, after an encode error and when a reader falls behind (`AUSocket` queue > 3 units is emptied, never buffered). A display size change (rotation) rebuilds the encoder. `stream.start` replaces a running stream; `Session.close` stops it. Never flush the encoder under `StreamSession.lock`: `CompleteFrames` waits on the output callback, which takes the lock (a deadlock at full size). Measured on an iPhone 17 sim (2026-11-05): scrolling 57.5 fps at 588×1280 (gap p95 17.7 ms, ~3.6 Mbps), 57.3 fps at 1206×2622, still screen 1 keepalive/s at ~0.1 Mbps, helper CPU ~0.05 core. No TS driver method yet (the `warden-stream` publisher, STRM-4, is the reader).
- **`touch.down{x,y,pointer?=0,unit?}`, `touch.move{…}`, `touch.up{x?,y?,pointer?}` → `{down, hidUs}`, `touch.cancel` → `{down, released}`** (`Ops/LiveTouch.swift`, `Ops/StreamingHIDSink.swift`; plan WDN-STRM STRM-6): a live finger, each op one HID event at once. Portrait-up points like the other input ops (`norm` uses the oriented screen). `LiveTouchState` is the pure state machine: one held finger is `touch`, two are `twoFingerTouch`; the HID cannot lift one of two fingers, so that lift is a `twoFingerTouch(.up)` and the other finger is pressed again (a new contact) on its next move. Move/up on a pointer that is not down, or a second down, is `E_BAD_REQUEST` `detail.reason` `not_down` / `already_down`; a finger with no down/move for 10 s is lifted by the watchdog (`LiveTouch.expire`). **One HID operation per gesture**: `StreamingHIDSink` keeps one `send(events:)` open from the first down to the last up (under the HID gate, so other input waits for the lift) and each op returns when idb pulls the next event, i.e. once its event was delivered. Measured on an iPhone 17 sim (`native/scripts/touch-bench.ts`): a drained `send(event:)` per event was ~92 ms, undrained ~8.6 ms, streamed 0.09 ms p50 / 0.27 ms p95 in the helper, 0.47 / 0.95 ms per move through the driver. `Session.close` lifts any held finger. TS side: `ios-driver.ts` `touchDown`… (`LiveTouch`, timeout 2 s; an older helper's unknown op is `helper_outdated`, remembered).
- **Key pacing** (`Ops/Keyboard.swift`, `Ops/Input.swift`): `key` / `typeText` / `selectAll` take `paceMs` (quiet after each key, default 5), `holdMs` (down to up, 20), `repeatGapMs` (extra before a repeated key, 50), and `typeText` `leadMs` (extra between the first key and the second, 60), each 0..1000. `WARDEN_SIMD_PACE_MS` / `WARDEN_SIMD_HOLD_MS` / `WARDEN_SIMD_REPEAT_GAP_MS` / `WARDEN_SIMD_LEAD_MS` change the defaults. The plan is pure data (`KeyboardMap.KeyStep`: `.event` / `.pause(ms)`); `InputEngine.stream` feeds it to idb's `send(events:)` as one HID operation (one drain at the end) through `PacedKeyEvents`, which sleeps each pause inside `next()` with zero timer tolerance (`ContinuousClock().sleep(for:tolerance:.zero)`), so a pause starts after the previous key was delivered and a cancelled op ends its sleep, instead of idb's `.delay`, whose timers a loaded host stretched (~260 ms/char on the EAS VirtualMac against ~99 locally). Taps, swipes, gestures and the unpaced `paste` chord stay composites. Measured on a local sim against the example app's controlled React Native input (`native/scripts/smoke.ts --focus-types <n> [--via type]`): 30/40/300 (the old defaults) cost ~99 ms/char with no loss, 5/20/50 ~38 ms/char with 0 lost characters in 90 strings and 30 fills, hold under 20 drops the character after a shifted one ("Hllo"), 0/0/0 is ~5 ms/char but loses 3-6 strings in 80. `driver/ios/type-budget.ts` sizes the request timeout (~100 ms per character, 200 per repeated key). Lead-in (2026-10-29, `--focus-types 80 --via type`, host busy with other simulators): without it 5/20/50 lost 8 of 80 strings, every loss in the first two characters (`"Hllo"`, `"Hllo, World 123!e"`, `"lol, World 123!H"`: the controlled input re-renders on its first change and the second key lands in it); a 60 ms lead-in lost 0 of 80 at ~41 ms/char; pace 20 also lost 0 but costs ~54 ms/char, pace 10 lost 1.
- **Focus before keys** (`screen/field.ts` `tapToFocus`, behind `fill` / `clear` / `type` / `press` and `warden ui fill`): UIKit never sets AX `focused` on the first responder text field, so `ElementBuilder` reports `focused: true` for the `is-editing` trait (`driver/ios/normalize.ts` does the same for a helper built before that). After the tap that moves focus, iOS hit-tests the tap point every 20 ms (`FOCUS_POLLS`, ~0.75 s at most) until the field reports focus; keys sent before that reach a controlled React Native input during its focus re-render (`setFocused` in an `onFocus`) and lose or reorder the first letters (`"Hllo"`, `"lol, World 123!H"`): 5 in 400 tap-then-type runs, 0 in 300 that waited (+85 ms after a field switch, +112 ms when the keyboard has to come up) and 0 in 200 that re-tapped an already focused field. A field already focused (spec `type` / `press` then skip the tap and type at its caret), Android, a bare coordinate, or a hit-test that cannot tell (another element at the point, e.g. content moved up for the keyboard) are not waited on. `warden ui press` + `type` and a spec's `press` + `type` do not go through it. `native/scripts/smoke.ts --focus-types <n> [--focus-mode cold|switch|same] [--raw-tap]` measures it.
- **`selectAll`** (`Ops/Keyboard.swift` `KeyboardMap.selectAll`, `Ops/Input.swift`): Cmd+A, held and paced like a key (`paceMs` / `holdMs` apply). `driver/typing.ts` `SelectsAll` / `canSelectAll` is the optional capability; `screen/field.ts` `focusAndSelect` selects plain text on a driver that has it; `focusClearType` then puts the text over the selection with no Backspace (a paste on iOS, see **`pasteText`** below; typed otherwise), and `focusAndClear` (`clear`) deletes it with one (an empty field or a placeholder shown as the value gets no keys; secure fields are backspaced by their bullets, as they cannot be read back), and a fill that does not confirm retries with counted Backspaces (`ClearMethod` `counted`), for fields that refuse the shortcut. iOS reports `placeholder: null` for React Native inputs, so a plain field showing its placeholder is indistinguishable from one holding that text: it takes select-all, never one Backspace per placeholder character. `clear()` reads it back through `clearedValue` (`screen/locator.ts`): a value that is not a subsequence of the pre-clear text can only be that placeholder, so it counts as empty An already-empty field showing its placeholder reads as its own text and deleting changes nothing, so after the counted pass `clear()` types one probe key (`CLEAR_PROBE`, `1`): a field that then holds just the probe was empty; the probe is deleted either way.
- **`pasteText` / `fill` `via`** (`driver/typing.ts` `PastesText` / `canPasteText`, iOS `ios-driver.ts` `pasteText`): `simctl.pbcopy(text)` (devicectl, then simctl, each confirmed by `pbpaste`) then one `paste` request (Cmd+V); empty text does nothing. It is the helper `typeText` already uses for unmappable characters. `locator.fill(text, { via })` and `warden ui fill --via type|paste` default to `"type"`; paste is opt-in because CoreDevice (Xcode 27.1) syncs every sim's pasteboard with the Mac clipboard both ways, also with no Simulator.app / Device Hub window: `devicectl device pasteboard copy` lands in the Mac clipboard (and clipboard managers), and from there on every other booted sim, so parallel runs can paste each other's text. A private `NSPasteboard` pushed with SimPasteboardPlus is ignored in the sim ("CoreDevice pasteboard stack is in use"); an item marked `org.nspasteboard.TransientType` is not synced but also cannot be read back to confirm the write (untested as a paste source). With `"paste"`, `field.ts` `focusClearType(…, via)` runs the focus tap and select-all as before, then pastes over the selection (secure fields too, after their Backspace-per-dot clearing) instead of typing: ~400 ms flat against 70-260 ms per typed character. Fallback order: a driver without `pasteText` (Android) types; a failed paste (`E_IO` pasteboard unconfirmed, a failed Cmd+V) types in the same attempt; the retry after a failed read-back (`clearMethodFor(2)`, counted Backspaces) always types, so a field that mangles a paste (mask, `maxLength`) still ends right. The read-back confirm is unchanged. `type()` / `clear()` keep keystroke semantics. `warden ui record` writes `via: "paste"` on a fill step only when it was pasted (codegen emits `{ via: "paste" }`); `via: "type"` from journals recorded while paste was the default still parses and generates no option. FakeDriver offers it with `pasteText: true` (recorded as `pasteText`).
- **`health`**: `ax.bridge` is `available | missing | failed | degraded`. `degraded` + `ax.lastError {message, agoMs}` means the guest is present but the last read failed (the next good read clears it). `health{probe:true}` (what `--health` runs) reads through the bridge and reports `failed`. A fresh `--health` process has no read history, so `warden doctor` also asks the running helper's socket.
- **Tracing**: `--trace` or `WARDEN_SIMD_TRACE=1` logs one debug event per quiescence sample; `--verbose` logs more; the log file is `~/.warden/simd/<udid>.log`.
- **AutomationEnabled**: the bridge needs `com.apple.Accessibility` `AutomationEnabled`. `ios-driver.ts` reads the sim's plist with `plutil` (~10 ms) and only runs `simctl spawn defaults write` (300-500 ms) when it is not already true.
- **Non-public API** (breaks first on a new Xcode): `Simulator.defaultHIDTransport` (mirrored in `Session.negotiatedTransport`: DTUHID from CoreSimulator 1155.4, else Indigo), `SimulatorDeviceOrientation.hidOrientation` (mirrored in `Session.hidOrientation`), the CoreDevice orientation service (a failed read falls back to `OrientationMemory`, `source` `written` / `assumed`), plus idb's private CoreSimulator and Accessibility use.
- **After an Xcode update**: `bun run --cwd packages/e2e native:build`, `swift test --package-path packages/e2e/native/ios`, `dist/warden-simd --health --udid <udid>` (expect `ax.bridge=available` and the right `hid.transport`), then `bun native/scripts/smoke.ts --udid <udid>` on a leased sim with the example app (`--kill-bridge` / `--kill-helper` exercise recovery). `warden doctor` shows the idb and Xcode versions the helper was built with.

## HID-loss recovery (iOS)
`Session.recoverHid` (`driver/ios/hid-recovery.ts`): a test that fails with `E_HID` (dtuhidd connection invalidated) or `E_NOT_BOOTED` (Device Hub's normal quit shuts every booted sim down) resets the driver and devtools, stops the resident `warden-simd`, reboots the leased sim once, runs `WARDEN_AFTER_REBOOT` (before the AX warm-up, so a reopened Device Hub window is in place before the helper takes the sim's HID) and runs the test again. `WARDEN_AFTER_REBOOT` is a JSON argv (`{udid}` replaced; `E2eEnv.afterReboot`) so this package never imports `apps/cli`: `warden` sets it to `warden arrange --open {udid}` for non-headless macOS runs (reopen the sim's Device Hub window, tile again); best effort, a failure is logged only.
