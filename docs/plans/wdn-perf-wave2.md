# WDN-PERF Wave 2: wall-time and cold-boot work from the e2e audit

> Status: implemented and unit-verified in a Linux container (no simulator or emulator); the device checklist is open. Stacked on `claude/wdn-perf-wave1` (PR #32); finding ids refer to the audit report in PR #31 (`docs/audit/wdn-perf-audit-2026-10-16.md`, raw files `docs/audit/raw/<nn>-*.md`).

## Context

Wave 1 landed the correctness and flake fixes. Wave 2 takes the wall-time and cold-boot items that can be built and unit-tested against the fake drivers and fake exec, and leaves the timing to the device checklist: the Android quick-boot snapshot (on by default, per the interview), the iOS claim path, the headless hide, the `warden e2e` pipeline barriers, launch waits, the fingerprint memo and build-cache pruning, bench fidelity, the tap hit-test, binary size, and `warden ui` state hygiene. Swift (`warden-simd`) and Java (`warden-uiad`) halves of the audit's items wait for a toolchain run and are listed under "Not in this wave".

Decisions applied (interview, report section 9): Android snapshot on by default with `android.snapshot: false` / `WARDEN_ANDROID_SNAPSHOT=0` opt-out; `typescript` resolved from the analysed project; build cache pruned from `warden gc` at 20 GB; contracts additive only; bench runs from a user shell.

## Review

Each merged cluster was read by an adversarial reviewer (one per cluster) that traced findings from a real caller or input to a failure. Their blocking and should-fix findings went to a fix round in fresh worktrees, where each finding had to reproduce as a failing test before any code changed. No finding was refuted: every one a fix agent took on reproduced. Device-only assumptions were collected into the checklist below rather than coded around.

### Open questions from the fix round

1. android-golden: should foreground `warden gc` skip the snapshot build and leave it to the `--quiet` pass and `golden ensure`? It runs under the spinner and can take minutes. Is 6 h the right wait before retrying a failed build?
2. tap-hit-test: once `Uia.setText` re-reads focus and passes on a device, should `setText` become the default for `auto` again?
3. bench-fidelity: write exit charges to `resources.ndjson` for diagnostics? Report the rusage of `start`ed children at exit too (which framework window to charge is the open point)?
4. fingerprint-memo: keep the memo for script configs that only use `join`/`resolve` calls (needs a real parse)? `builds prune` with a bad `WARDEN_MAX_CACHE_SIZE`: fall back to 20 GB with a warning instead of exit 1?
5. headless-hide: is 2 min of margin over `BOOT_TIMEOUT_MS` enough for a stale detach row, given `simctl boot` itself has no timeout?
6. ios-claim-path: delete an expired quarantined warden device when there is no room, instead of leaving it quarantined?
7. launch-wait: add an optional `Element.package`, filled by both Android parsers, so the content gate can ignore system overlays?
8. ui-state-hygiene: should `stopHelperAfter` also print the helper warning to stderr?
9. batch-pipeline: should `warden run` also drop a device the headless hide cannot boot again, or keep failing on it as it does now?
