### 6. uiad suppression — ✅ confirmed, ✅ fix works
- `warden ui snapshot` with TalkBack bound (`Bound services:{Service[label=TalkBack…` before) → after: `Bound services:{}` and the resident `app_process … warden.uiad.Main` stays; `Enabled services` still lists TalkBack. TalkBack process stays alive but unbound. `kill <uiad pid>` → TalkBack rebinds in <3 s.
- Patch `invoke(withFlags, 1)` (`UiAutomation.FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES == 1`; used `connect(int)` reflection already in place, 21–58 ms connect): TalkBack **stays bound** through connect, snapshot, tap, key, a11y actions; `stock service info flags=0x10012`.
- `uiautomator dump`: ⚠️ **transiently unbinds** TalkBack for the dump's lifetime (~1 s), then TalkBack rebinds ≈2 s later (`Bound services:{}` during, bound again after). It restarts TalkBack (loses a11y focus). So the dump fallback is unusable in TalkBack mode.
- Decision A11Y-1/7: connect with `FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES` (1) **always** (no harm with TalkBack off; avoids a reconnect when the condition flips mid-run). TalkBack mode requires uiad; if uiad is off/unsupported → `E_UNSUPPORTED` with hint, never fall back to `uiautomator dump`.

### 7. Driving under TalkBack — ✅ (with flag 1)
- `findFocus(FOCUS_ACCESSIBILITY)` on `getRootInActiveWindow()` works: returned the TalkBack cursor node with `a11yFocused=true` (e.g. `search_action_bar` initially).

Works on non-focusable title TextViews too, but then TalkBack speaks only that text; focusing the *focusable row* speaks the merged row ("Network & internet. Mobile, Wi‑Fi, hotspot. 4 of 28"). → resolve to the nearest focusable ancestor (what TalkBack itself would land on).
- `ACTION_CLICK` on the focusable/clickable ancestor: `true`, Settings navigated (`SubSettings` focused window) — no coordinates needed. `ACTION_CLICK` on a non-clickable node → `false` (climb to the clickable ancestor).
- `ACTION_SCROLL_FORWARD` on a non-scrollable child → `false` (target the scrollable ancestor).
- **Normal warden `tap` with TalkBack bound (flag 1):** one injected tap (`via inject3`) at an item **activated it directly** (TalkBack 17 default "Single-tap to activate", Advanced settings → "Single-tap to activate"); focus moved and item opened. So today's `press` works on this TalkBack version, but depends on that setting/version → use ACTION_CLICK.
- **Normal warden `swipe` (one finger, up):** did **not** scroll (list bounds unchanged); TalkBack treated it as navigation (next/prev focus, spoke "Search Settings. Out of list"). → `scroll` must use `ACTION_SCROLL_FORWARD/BACKWARD` on the scrollable.
- Keyboard: `input keyevent KEYCODE_TAB` (first press only landed initial focus on search bar, second moved to next row), `KEYCODE_DPAD_DOWN` / uiad `key` op move TalkBack focus. Alt+Right was a no-op, Alt+Down jumped ahead many rows (to "27 of 28") — Alt+arrow semantics unclear; don't use. Dpad/Tab next-prev work but are not exact one-item steps in every case.
- Decision A11Y-5/7: `screenReader.focused()` = `findFocus(FOCUS_ACCESSIBILITY)`; `.activate()` = ACTION_CLICK on focused node's clickable ancestor; `.next()/.prev()` = **TalkBack's own traversal**: send `AccessibilityNodeInfo.ACTION_NEXT_HTML_ELEMENT`-free approach — prefer `KEYCODE_TAB`/`Shift+Tab` via uiad `key` (verified moves focus; spoken text then identical to real swipe-nav, incl. "N of M"). Not yet tried: focus traversal via `performAction(ACTION_NEXT_AT_MOVEMENT_GRANULARITY)` or `GLOBAL_ACTION` — optional follow-up. `press`/`scroll` in TalkBack mode: ACTION_CLICK / ACTION_SCROLL_*.

  Alternative earlier line: `EventTypeViewAccessibilityFocusedFeedbackRule: … ttsOutput={…}`.

### 11. Reduce motion + display settings — ⚠️ plan assumption wrong
- **RN 0.86.3 `isReduceMotionEnabled()` follows `transition_animation_scale == 0`, NOT `animator_duration_scale`** (`AccessibilityInfoModule.kt:101-118` `isReduceMotionEnabledValue`; ContentObserver registered on `Settings.Global.TRANSITION_ANIMATION_SCALE` only, lines 241-242). Source-verified; not run in RN (see precondition).
- **Clash**: `disableAnimations()` (`packages/e2e/src/driver/android/android-animations.ts`, `animationScaleArgvs()` in `android-argv.ts:285`) sets window, transition and animator scales to 0 on every driver open and restores the originals on close (saved in `android-state.ts`). So every e2e run (and `warden ui` session: observed) already has RN reduce-motion **true** — a spec asserting `reduceMotion: false` behaviour cannot work today, and `reduceMotion: true` is a no-op that the driver restore would also undo.
- Live apply (throwaway app with ContentObservers, `settings put …`, callbacks in <0.5 s each): `global transition_animation_scale`, `global animator_duration_scale`, `secure high_text_contrast_enabled`, `secure accessibility_display_inversion_enabled` **all fire live** and read back the new value; `window_animation_scale` not observed. Actual visual inversion not pixel-verified (`screencap` skips the SurfaceFlinger color transform).
- Decision A11Y-6: `reduceMotion` condition = set **only** `transition_animation_scale` (0 for true, `1.0` for false) *after* the driver's `disableAnimations`; the driver then needs a "motion" mode: `reduceMotion: false` → driver leaves `transition_animation_scale` at 1.0 (and warns that animations are on), keep window/animator at 0. Undo/restore must go through the driver's saved originals (`android-state.ts`), not delete. Defaults: `high_text_contrast_enabled` / `accessibility_display_inversion_enabled` read `null` originally → undo = `settings delete secure <key>`; same for `animator_duration_scale` (originally `null`, `settings get` → `null`, but a restore `put`s it).
