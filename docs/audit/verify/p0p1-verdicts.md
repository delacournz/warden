Full reasoning per lens is in `p0p1-verdicts.jsonl`.

## Reasoning (mechanism lens, then impact lens)

### 05-1 alert("accept") presses "Don't allow" on Android 11+ runtime-permission prompts

- M (holds, holds, → P1): detectAlert collects every element whose id is in ALERT_BUTTON_IDS, in tree order, including foreground_only, one_time and deny. device.alert('accept') uses firstOf(ACCEPT_BUTTONS) and otherwise falls back to buttons[last]. findButton needs an exact case-insensitive match, so 'While using the app' and 'Only this time' match no entry in ACCEPT_BUTTONS, which holds only iOS-style labels. In the AOSP layout the deny buttons come after the allow ones, so the fallback lands on deny (or 'deny and don't ask again'). The only fixture in the repo is the two-button allow/deny dialog, so nothing pins the three-button case. The exact labels and order still need an API 30+ device dump.
- I (holds, holds, → P1): detectAlert collects every visible permission_* button in tree order. ACCEPT_BUTTONS holds only iOS labels, matched exactly, so 'While using the app' and 'Only this time' match nothing. The fallback then takes the last button, which in the AOSP grant dialog layout is permission_deny_button. Repo fixtures only cover the two-button dialog. When it fires, the result is deterministic: the permission is denied every time on API 30+ for camera, mic or location. But neither the example nor the bench exercises that path, and alert({button}) is a workaround. That makes it a correctness bug on a narrow path, so P1 is fair, not P0. Confirming the labels needs a device dump.

### 09-5 Android app.open() fails whenever WARDEN_LAUNCH_ARGS is non-empty (always with Metro --initialUrl)

- M (holds, holds, → P1): app.ts:73 always passes `[...env.launchArgs, ...]`. android-app.ts:62-67 returns E_UNSUPPORTED for any non-empty args, and unwrap throws on it. specLaunchArgs (launch.ts:39-42) prepends `--initialUrl` whenever metroUrl is set, with no platform check. e2e.ts:393 feeds it into every job env, and batch.ts:1180-1185 sets metroUrl for any platform; Android only gets an adb reverse (batch.ts:1066). A real suite hits this: apps/example's `example-dev` enables Metro with launchArgs (warden.config.ts:104-108). app.test.ts has no Android test with non-empty launchArgs. The failure is deterministic, so no device is needed.
- I (holds, holds, → P1): This one is deterministic. app.ts:72-77 always sends env.launchArgs. android-app.ts:62-67 returns E_UNSUPPORTED for any non-empty args. specLaunchArgs puts --initialUrl first whenever metroUrl is set (launch.ts:39-42, e2e.ts:393), and Android batches do get metroUrl (batch.ts:1180-1185), with only adb reverse in openOnDevices (batch.ts:1066). Every app.open fails on any Android suite that uses Metro or spec.launchArgs. The repo's only Metro suite (example-dev) is iOS, and the bench forces '[]', so it does not fire today. P1 fits, rising to P0 the moment someone adds an Android Metro suite. The fix is small.

### 10-1 Session turns lost after ~2 s and is never revived

- M (holds, cannot-tell, → P1): The reconnect budget is 10 attempts with 200 ms sleeps between them, about 2 s, and establish() fails fast when listTargets/selectTarget finds no target (session.ts:148-156, 186-221). After that the state is 'lost' and current() returns the stored error forever (:224-229). Nothing outside the collector listens for 'lost'. The owner keeps devtoolsOpening/facet after a successful open and only clears it when the open fails (packages/e2e/src/session.ts:220-234). react-locator swallows tree failures and returns [] (react-locator.ts:36-41). app.open relaunches the app (app.ts:67-80). The code path is sound. How often a relaunch takes longer than 2 s can only be checked on a device.
- I (holds, cannot-tell, → P1): The finding is confirmed. There are 10 attempts with 200 ms backoff (session.ts:17-18). After that the state is set to lost and never cleared (211-214), and current() returns the stored error from then on (224-229). The owner caches devtoolsOpening once it succeeds (src/session.ts:220-231). There is no Metro in Release builds, so neither the bench nor Release runs are affected (fixtures.ts:19-28). The React accelerator is only a fallback for testIDs missing from the AX tree (context.ts:160-165), so most locators keep working. Specs that use device.devtools.* after a relaunch longer than 2 s in a dev client fail outright, and how long dev-client relaunch takes still has to be measured on a device. P1 is defensible for dev-client runs.

### 11-2 Landmark check turns moved into absent so negative assertions pass falsely

- M (holds, holds, → P1): Confirmed. LAZY_KINDS (wait/is/get/scroll) skips the eager placement, so these targets are resolved only through ctx.find. find runs toLocated -> resolveTarget, which turns both a role change and a move beyond the 40 pt landmark tolerance into {missing}. In flow-actors, present/showing need 'resolved'. So `is hidden` gets entry === undefined and reports hidden = true, while `wait detached` and `wait hidden` succeed at once. `wait visible` and `wait attached` poll until the budget runs out. `scroll until` keeps swiping. I found no guard against this. The existing replay tests cover the landmark only for eager press steps.
- I (holds, holds, → P1): Traced the path. resolveTarget turns a role change, or a move of more than 40 pt, into a divergence (replay.ts:242-250). toLocated maps that to {missing} (replay.ts:267-270), and find returns it to the actors (replay.ts:387-394). There, present/showing are false (flow-actors.ts:67-68), so wait hidden or detached is reached at once, and `is hidden` takes entry===undefined as true (flow-actors.ts:178-188). The result is a false green on a negative assertion whenever the element reflows by more than 40 pt, which is common with banners, keyboards and list changes. A positive wait burns its whole budget and then gives the wrong reason. A silent false pass in a test runner is a real correctness gap, and the fix is local, so P1 stands.

### 12-2 Auto-gc spawned just before the claim races the claim for idle booted sims

- M (holds, cannot-tell, → P1): Confirmed. runSession calls maybeAutoGc and starts claiming immediately. The claim inserts its lease only after its own provider.inventory(), inside the reserve transaction. It touches the device only in complete. In gc, the `leased` set is a snapshot taken before gcPlatform runs. gcPlatform then reads the records, awaits the inventory, and shuts down idle unleased records without re-checking the lease. iOS shutdown is a plain simctl shutdown with no lease check. So the interleaving the finding describes is possible. Whether it is likely depends on how long the gc process takes to start compared with the claim's inventory. The throttle (10 min) and the gcWork check do not prevent it. How often it happens needs a device.
- I (holds, cannot-tell, → P1): maybeAutoGc fires just before the claim (batch.ts:1615) and spawns a detached gc whenever an unleased device went idle after the last pass (autogc.ts:47-66, store.ts:362-373). The claim inserts its reuse lease only after its own inventory call (claim.ts:251,286). gc builds its leased set once (gc.ts:130-141). After that, gcPlatform awaits inventory and shuts down without checking the lease again (gc.ts:44-70). One correction: the snapshot is taken after several awaits (stale-lease handling, releaseDevices, the helper sweep), not 50-150 ms after spawn. So the lease has more chance of landing first, and 'likely' is unproven. The race between two warden processes is still real and breaks the leased-device rule. It fires on the first run after more than 20 min idle. P1 per the rubric. Fix (b) is proportionate.

### 16-1 Auto-gc started by a claiming command shuts down the idle device that same command is about to reuse

- M (holds, cannot-tell, → P1): The ordering is as described. claim.ts calls maybeAutoGc before claimWithFlags, and runSession does the same in batch.ts. gc reads `leased` once at gc.ts:129, then runs a slow inventory and shuts down whatever is idle per that snapshot. Nothing re-checks inside a transaction and gc takes no lease of its own. The claim's lease is inserted only after its own inventory (claimDevices -> tryReserve). 'Shutting Down' falls through to 'booting' (ios.ts:46,94), which allocate ranks above shutdown and treats as reuse, and realise then skips boot. I found no guard. Still, who wins the race (gc child startup plus stale-lease work vs the claim's simctl list) is timing that only a device can settle. Case (a), a run failing outright, is plausible but unmeasured, so P0 is not earned.
- I (holds, cannot-tell, → P0): The code supports the ordering. maybeAutoGc fires before the claim in claim, batch, run and dev. gc takes its `leased` set and `records` once, then runs inventory and shuts down without re-checking inside a transaction. gcWork counts a device that went idle after the last pass, and nothing runs gc during a quiet gap, so the first e2e after more than 20 min while the sim is still booted spawns gc. On the e2e path the claim reserves only after Metro, ports and its own inventory, so gc probably wins the race. Whether that costs a cold boot (at least 6.5 s, already P1) or fails the run (P0) depends on timing that only a device can show. It fires at most once per gap.

### 16-2 A device that never gets ready is neither quarantined nor retried, and is picked first again next time

- M (holds, holds, → P1): realise returns `{ ok: ready, leaseId }` with no `unhealthy` when waitReady fails (claim.ts:195-196), so complete counts it as a hard failure: it deletes every lease of the round and returns err without quarantine or retry (:333-339). Only a failed probe gets into quarantineUnhealthy and the retry loop. allocate ranks booted/booting first (STATE_RANK, allocate.ts:58,80-82), and isWarm only skips waitReady when the device is booted and verifyWarm passes (:152-155). So a wedged device is picked first again and waited on again. I found no guard one level up in claimDevices/settle.
- I (holds, holds, → P1): realise returns {ok: ready} with no `unhealthy` on a waitReady failure (claim.ts:195-196), so complete fails the whole claim and only deletes leases (:333-339). Nothing shuts down or quarantines the device. allocate sorts free devices by STATE_RANK, booted/booting before shutdown (allocate.ts:58,80-82), so the leaseless stuck device comes back first on the next claim. If verifyWarm fails again, so does the next 300 s bootstatus. A wedged boot is rare, but when one happens it fails every run, costing 300 s each time, until gc or a human steps in. P1 fits as a real robustness gap. The fix is small and proportionate, as long as reused devices get a shorter budget.

### 17-1 K8a: expo prebuild moves the native fingerprint mid-build; runLocalBuild refuses to cache, and re-keying alone still rebuilds for device 2 and other worktrees

- M (holds, overstated, → P1): local.ts:168-172 recomputes the key and refuses on any change. ensure.ts:210 propagates the error, and the test at local.test.ts:129 pins that refusal as intended behaviour. The project's own plan (wdn-perf.md:664,690) records the mid-build fingerprint move as seen on a device, so the trigger is real. Extensions (a)-(c) follow from the code: prepare is memoized per platform, fetchOrBuild re-checks steps.cached() with the pre-build hash, and recordInstall stores that hash. P0 overstates it, though. On a second run in the same worktree ios/ or android/ already exists, so the pre and post keys match and the build caches. The failure is a one-time cost per fresh worktree.
- I (holds, holds, → P0): local.ts:168-172 refuses whenever the post-build key differs. apps/example build.ios runs expo prebuild and android runs expo run:android, and both create gitignored native dirs. The measured evidence is real: wdn-perf.md:664 says the perf-android-r1/-r2 runs never reached the tests, and the ios bench doc line 121 records the hash move. This fires on the first `--app` run in every fresh worktree and fails it after minutes of building, which is P0. The device-2 and other-worktree rebuild points follow from the cache being keyed on the pre-build hash, but I did not re-trace them. The alias-row fix looks proportionate, but it can only be confirmed on a device.
