The run behind the 2026-10-25 iOS dataset on the [comparison page](/docs/bench/comparison). Everything below comes from the four workers' artifacts, merged into one report; nothing was measured on a developer machine.

## How it was run

| | |
|---|---|
| Workflow | `apps/example/.eas/workflows/bench-baseline.yml`, EAS Workflows run [`01a172f5-fdee-7992-b66c-a2173338eb32`](https://expo.dev/accounts/delacour/projects/warden/workflows/01a172f5-fdee-7992-b66c-a2173338eb32), inputs `runs=5`, `frameworks=warden,argent,agent-device,tester-army`, `max_minutes=55` |
| Code | warden commit `5ffd64f2` (branch `feature/devboxes`), every suite under `packages/e2e-bench/suites/` |
| Workers | One EAS `macos-large` worker per framework, four in all, two at a time on this plan. VM template `macos-tahoe-26.5-xcode-26.6`: VirtualMac2,1, Apple M4 Pro (Virtual), 10 cores, 40 GB, macOS 26.5.2 (25F84), Xcode 26.6 (17F113) |
| Simulator | Each worker claims its own headless simulator with `warden claim ios --headless` (iPhone 17, iOS 26.5, named `warden-iphone-17-1`), created fresh for the job and shut down at the end. Nothing one framework leaves behind can reach another |
| App | The same build on every worker: `nz.co.delacour.warden.example`, EAS `bench` profile (Release, simulator), sha256 `2d35643eda49`, 101.1 MB, reused by fingerprint (`build_ios` skipped), installed with `simctl install` before the bench |
| Runs | 5 runs of the 8-test suite per framework. Run 1 is cold; warm numbers are the median of runs 2 to 5. `retries=0`, fresh app launch per test, `caffeinate -dims` held |
| Before the bench | `bun install`, `warden-simd` built from source (Swift release), the framework installed (`bun add -g @swmansion/argent@0.30.1` / `agent-device@0.21.31`; tester.army's `e2e` 0.20.0 comes with `bun install`, Node 22.23.1), then the job waits for the 1-minute load average to drop under the core count and records a 60 s idle control of the simulator with the app in the foreground |
| Deep-link sheet | iOS shows "Open in …?" for the first custom-scheme link after a boot and never again, so the harness opens one link and answers the sheet before every framework's prepare. No suite handles the sheet itself |
| Hard stop | A watchdog stops the bench at `max_minutes`; it did not fire on any worker (the longest job ran 28 min) |
| Isolation per framework | Helpers of every framework stopped, driver apps uninstalled before the run (cold cost measured), residue listed after teardown |
| Sampling | Host and simulator processes sampled every 500 ms from `ps`; the CPU headline is CPU-seconds of the framework's own process tree during the timed run, warm median |
| Evidence on exit | Each job screenshots the simulator and lists the apps still running, releases the lease even when a step failed, and uploads an `eas-ios-<framework>` artifact |
| Versions | bun 1.3.14, warden 0.1.1, Argent 0.30.1, agent-device 0.21.31, tester.army e2e 0.20.0 (bundled agent-device 0.21.25), Node 22.23.1 |

Hosted workers idle hotter than a Mac and share their host, so these numbers compare only with other `macos-large` runs, never with the local 2026-10-16 runs.

Sampled every 500 ms from `ps`. `host` = the framework's own process tree; `sim` = every process of the simulator's `launchd_sim` tree, or on Android the app under test plus every framework's on-device helpers from `top` (every 2 s). RSS is a per-process sum, so shared framework pages are counted once per process: compare the numbers across frameworks, not against physical memory.

`CPU-s / rep` (the CPU headline) is the CPU time of the timed run only, median over the warm reps (over every rep, cold included, when a framework has no warm rep, as with `--runs 1`), from per-process deltas of `ps time`; the other columns are whole-framework (prepare, every rep, the per-rep housekeeping and teardown), so their averages move with suite length. `CPU avg` / `CPU peak` are `ps %cpu`, a decaying average on macOS, kept for comparison with older runs. Android `sim` has no CPU-seconds (`top` only). CPU-seconds undercount: CPU a process uses after the last 500 ms tick, and processes living between ticks, are only recovered for children the bench ran itself (their rusage at exit); daemons and processes a framework spawns and never waits for are not, so frameworks that fan out to many short-lived tools read low. An exit charge is booked to its root's group, so in the per-group split the unseen CPU of a descendant of another group (a `bun test` under a `warden` root) shows under the root. procps (Linux) `ps time` has 1 s resolution.
