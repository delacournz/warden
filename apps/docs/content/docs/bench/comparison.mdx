## Cold start, prepare, teardown

Cold-start cost is the first run minus the warm median, plus the time spent in prepare: what installing a runner app or starting a daemon costs, not steady-state speed. Overhead is suite wall time minus the sum of test durations.

A negative cold-start cost is not a duration. It means the cold first run finished faster than the warm median (run-to-run noise on a framework with little startup cost), so the table shows "none (rep 1 not slower, ...)" and leaves it out of the fastest-cell highlight.

## Resources

CPU is judged in CPU-seconds per rep: the CPU time the framework's own processes used during one timed run (warm median), from per-process deltas of `ps time`. The sampled `%cpu` is shown last as a secondary number. Memory is the framework's own processes, sampled every 500 ms.

## Fairness rules

- Same `.app` for every framework, with its sha256 recorded.
- Zero LLM calls.
- Same assertions per canonical test id.
- Same retry helpers: dropped first tap, dropped deep link, system alerts.
- The iOS "Open in …?" sheet is answered once per boot by the harness before every framework's prepare (iOS asks it for the first custom-scheme link after a boot, not again).
- Fresh app launch per test, `retries=0`.
- Frameworks run sequentially with daemons stopped between them, or, on EAS, each on its own worker and simulator.
- `caffeinate -dims` held for the run, host otherwise idle, load average recorded.
- Warm medians exclude rep 1.
- Machine-readable reporters only.
- A framework with any failing test never sets the pace, so it is never the fastest.

## Caveats per framework

| Framework | Gap |
|---|---|
| warden | Copied from the example app, retries written with warden's own options: `tap({ until })`, a deep-link retry, `systemAlerts: "dismiss"`. The hand-rolled helpers it replaced ran the published headline numbers; the idiomatic run is reported beside them. |
| Argent | Retries are nested `when:` guards capped at two retaps. Flow selectors read only the app's view hierarchy, never SpringBoard, so the flow cannot answer the "Open in …?" sheet itself. A checkbox's checked state is not readable, so the remaining-count assertion covers the effect. |
| agent-device | `.ad` scripts have no retry or conditional, only `wait` and `press`, so the deep-link script cannot answer a sheet that may or may not show. Needs a runner prepare step and a daemon. |
| tester.army | Has its own copy of the hand-rolled helpers warden used before. Runs with a private agent-device state dir and Node 24 on `PATH`. |

Each run is a snapshot on one machine class with few warm repetitions: read the ratios as a guide, not a verdict. The full Markdown report for each run is in `docs/bench/` in the repo; the EAS runs also publish every worker's artifact on their run page.
