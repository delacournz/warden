description: One command from a cold shell runs a suite on leased simulators, with warden owning the devices, the build and Metro.

---

```bash
warden e2e <suite>
```

That is the whole run. No device to pick, no port to export, no bundler to start first. warden claims the simulators, installs the cached build, starts and verifies its own Metro when the suite has one, runs the flows, and releases everything on exit (Ctrl-C included).

## Try it on the example app

`apps/example` in the warden repo carries two suites over the same five flows:

| Suite | Build | Metro | Spec processes |
|---|---|---|---|
| `example` | Release, JS embedded | none | one `bun test` per flow |
| `example-dev` | Debug dev client | warden's, on a leased port | one `bun test` per device, each running its share of the flows |

```bash
cd apps/example
warden e2e example --all        # Release build, 2 sims
warden e2e example-dev --all    # dev client + warden's Metro, 2 sims
warden e2e example-dev          # only the flows this branch touches
warden e2e example-dev --flows todos,settings
```

The first run of a native fingerprint builds the app (minutes); later runs reuse the cache.

The flows are `*.e2e.ts` specs written with [`@delacour/warden-e2e`](/docs/guides/specs) and run by `bun test` (bun 1.3 or newer on `PATH`, or `WARDEN_BUN`). A project that has no `@delacour/warden-e2e` yet fails before any device is claimed with `bun add -d @delacour/warden-e2e`.

## What a suite needs

```ts title="warden.config.ts"
"example-dev": {
  project: "example",
  flowsDir: "e2e",
  platform: "ios",
  app: { variant: "dev" },
  metro: { env: { EXPO_PUBLIC_E2E: "1" }, launchArgs: DEV_MENU_OFF },
  spec: { bundleId: "com.example.app" },
  mode: "single",
  count: 2,
  jobTimeoutMs: 15 * 60_000,
},
```

- `spec` says how the specs run: the app under test (`bundleId`, default the project's), extra `launchArgs` and the `timeout`, `actionTimeout` and `assertionTimeout`. See the [field reference](/docs/reference/configuration#e2e).
- `metro: {}` makes warden lease a port, start `expo start --dev-client` there in the project root, and call it ready only once that port is proven to serve **this** checkout. Another worktree's Metro on the port stops the run with `port <p> is served by <dir>, not this worktree`.
- `mode: "single"` runs one spec process per device, each with its share of the flows (sharded round-robin by flow id), instead of one process per flow.
- `jobTimeoutMs` kills a spec process that hangs (exit 124) so the run always ends.

The specs read what warden exports and need no config file of their own. With a Metro suite, warden passes `--initialUrl <metro url>` as the first launch argument, which is what the Expo dev client reads at launch, so every `app.open()` in a flow lands on warden's bundler.

## What a run prints

Each spec process prints one line when a test starts and one when it ends, and one pair per step (a tap, a fill, an assertion):

```text
[00:54:25.766] ▶ test |ios| e2e/todos.e2e.ts › adds a todo
[00:54:25.942]   ▸ todos › app app.open
[00:54:27.193]   ▪ todos › app app.open passed 1251ms
[00:54:29.470] ■ test |ios| e2e/todos.e2e.ts › adds a todo passed 3.21s on warden-iphone-17-2
```

The `[HH:MM:SS.mmm]` stamp is warden's: every line written to a job log, `setup-<worker>.log`, `metro.log` and `serve.log` starts with the local time it arrived, and spec processes get `WARDEN_LOG_TIMESTAMPS=1` so they print no clock of their own.

The batch log (and `--no-tui`) adds one line per finished test, read from `results.jsonl`, and the live grid ticks flows and tests off as they finish:

```text
✓ todos › adds a todo (3.21s)
✗ sign-in › a locked account shows the form alert (8.04s)
```

When the run ends, every failed flow is listed with its failing tests, the first line of each error and the artifact directory of each.

## Where to look when it fails

| What | Where |
|---|---|
| verdict per flow, and per test (`tests[]`) | stdout, and `e2e-report.json` in the batch dir (`--json` prints it) |
| every test's status, duration and error | `<batchDir>/e2e/<worker>-<seq>/results.jsonl` |
| a failed test's evidence | `<batchDir>/e2e/<worker>-<seq>/<flow>/<test>-<hash>/`: `failure.png`, `screen-at-failure.txt` (the full accessibility tree), `trace.jsonl` |
| a spec process's output | `<batchDir>/logs/<worker>-<seq>-<job>.log`, screenshot next to it |
| Metro's output | `<batchDir>/metro.log` |
| a device's driver warm-up | `<batchDir>/logs/warm-<worker>.log` |
| a device that keeps failing | `warden release <leaseId> --bad "<why>"` keeps it out of the pool |

`e2e-report.json` gives each flow `verdict`, `attempts` and `tests[]` (`title`, `status`, `durationMs`, `error`, `artifacts`). A flow fails when any of its tests failed or timed out, or its process exited non-zero. When a process wrote no `results.jsonl` at all (a crash before the first test), the verdict falls back to the exit code with a warning. Under `CI`, a `test.only` left in a spec fails the run and is listed under `only`.

Before the first flow, warden starts the iOS driver helper of every leased device at once and takes one accessibility snapshot on each (`warmDrivers`, on by default), so the first spec on a device does not pay the cold start. Jobs get `WARDEN_SIMD_SOCKET` and connect in milliseconds. `warmDrivers: false` on the suite, or `--no-warm`, turns it off; a failed warm-up only warns.

## Don't

- Start Metro yourself, or point a suite at a fixed port.
- Export `WARDEN_UDID*` / port env vars by hand for a suite. They exist only inside a run.
- Hold devices with a bare `warden claim` for a test run. It lasts about 5 minutes; `warden e2e` holds its leases for as long as it runs.
