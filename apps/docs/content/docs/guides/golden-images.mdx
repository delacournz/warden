A brand-new simulator's first boot takes 1–10 min, and about 80% of that is the one-time data migration. Measured:

| Scenario | Time |
|---|---|
| fresh create + first boot | 146–239 s |
| clone of a settled golden + boot | 3.7 s + 11.9 s |
| 3 clones booted in parallel | ~20 s |

So when `warden claim ios` needs a **new** pool device, it clones it (`simctl clone`) from a **golden image**: a sim warden booted once, waited on until its data migration finished (`DMLastMigrationResults`, since `bootstatus -b` can return early) and its CPU settled, then shut down.

- The golden is built on first use and keyed by Xcode build + runtime + runtime build + device type + recipe. An Xcode or runtime upgrade simply builds a new one.
- The golden also has the e2e driver's accessibility switch (`AutomationEnabled`) written in it, so a fresh clone's first driver open skips that in-sim `defaults write`. This is recipe 2: after upgrading to it, every machine rebuilds its golden once (a few minutes) on its next claim. The recipe-1 golden of that profile is deleted at the same time; run `warden golden ensure` to pay the rebuild ahead of time.
- Clones are APFS copy-on-write (~30 MB each).
- If cloning fails, warden falls back to `simctl create`. `WARDEN_GOLDEN=0` turns cloning off.
- A pool device that already exists is always reused first; a second boot takes ~6.5 s.
- Goldens are never allocated, adopted, booted by `gc` or counted in the pool; `warden devices` labels them `golden`.

## Commands

```bash
warden golden ensure --profile iphone-17   # build ahead of time, so the first claim doesn't pay
warden golden ls
warden golden prune                        # delete stale goldens; --all deletes every one
```

## Android: warden's quick-boot snapshot

Claimed emulators launch `-read-only -snapshot warden-<key>` from a quick-boot snapshot warden owns, instead of whatever `default_boot` your last Android Studio run left (or a full cold boot). The first claim of an AVD builds it: when no instance of that AVD is running, warden cold-boots it writable and headless (`-no-snapshot-load -no-snapshot-save`, so your `default_boot` is left alone), waits for `sys.boot_completed` plus a short settle, runs `adb emu avd snapshot save warden-<key>` and kills it; while that AVD is running the build is skipped and the claim cold-boots. The key covers the system image revision and build fingerprint, the emulator version, the AVD's `hw.*` settings and a recipe number, so an emulator or image update builds a new snapshot and `warden golden prune --platform android` (or the next build) deletes the stale one. A launch from the snapshot that fails is retried once as a cold boot. It needs `ANDROID_HOME` (or `ANDROID_SDK_ROOT`); each snapshot costs about the AVD's RAM in disk. Turn it off with `android: { snapshot: false }` in `warden.config.ts` or `WARDEN_ANDROID_SNAPSHOT=0` (`=1` overrides the config). Claimed emulators also run `-no-audio -no-metrics`; `WARDEN_EMULATOR_AUDIO=1` keeps audio. `warden golden ensure|ls|prune --platform android` builds, lists and prunes the snapshots.

## Cloning your own sim

`warden clone <udid|name> [--name x]` duplicates any **shut-down** sim — e.g. one you've set up by hand — into warden's pool. warden refuses a booted source rather than shutting it down.
