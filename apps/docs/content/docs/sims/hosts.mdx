A **host** is another Mac running its own warden: a Mac mini on your desk, one on Tailscale, an EC2 Mac, a teammate's machine. Your laptop's warden drives it over `ssh`. The host keeps its own lease store, sims, golden images and driver helper, so everything warden does locally works there too. No warden account is needed.

## Set a host up

```bash
# 1. record it and pin its host key (first contact)
warden host add mini --ssh me@mini.tail:22

# 2. install this warden version there, fetch the helper, grant this laptop's key
warden host setup mini

# 3. check it
warden host doctor mini
```

`host setup` uses your normal ssh key once, for a plain shell: it installs warden at `~/.local/bin/warden` (no sudo), runs `warden doctor --fetch-helper` there, and grants this laptop's own warden key (`~/.warden/hosts/id_ed25519`, made on first use). From then on the laptop only uses that key. Add `--golden` to also build the iOS golden image on the host. A dev or local build of warden has no release to download: pass `--binary <path>` to a warden built for the host.

A host with no inbound port (behind NAT, a CI runner) is reached with `--jump <bastion>` or `--proxy-command` (for example `cloudflared access ssh --hostname %h` or `tailscale nc %h %p`).

### A CI runner or a fresh Mac

A machine that can't take a normal ssh login, like a GitHub Actions macOS runner, can attach itself instead:

```bash
# on the laptop: the key to hand over
warden host key

# on the runner: a user-level sshd that lets in only that key (no sudo)
warden host attach --grant "ssh-ed25519 AAAA… warden:…" --advertise 100.64.0.9 --for 60m
```

`host attach` prints the `warden host add … --granted` line to run on the laptop. `--granted` means the runner already lets your key in, so there is no `host setup` step. The runner is reached on your tailnet (`--tailscale`, or `--advertise` with a userspace tailscaled), or through a bastion it dials out to (`--jump user@bastion --jump-port 2201`). The warden repo has an example workflow, `.github/workflows/remote-host.yml`, that keeps a macOS runner attached for up to two hours.

### No inbound at all: through warden-api

A Mac that can only dial out keeps one link to warden-api, and laptops in the same account reach it with their `warden login` session. Nothing listens on the Mac.

```bash
# on the Mac
WARDEN_HOST_TOKEN=… warden host uplink

# on the laptop
warden host add mini --cloud
warden host doctor mini
```

Commands over the relay go through the same allowlist and leases as ssh. `warden dev --host` still needs ssh, because Metro rides an ssh port forward. A hosted Mac's session end caps its leases, and they end with `LEASE_LOST` (`host_expired`).

## Claim a device on a host

```bash
warden claim ios --host mac --json
```

The host's warden does the claim: its own boot queue, capacity and golden images. The laptop records one lease per device it got, and `warden ls` shows them with a `HOST` column (`warden ls --hosts` for just those). `warden heartbeat` and `warden release` (with `--shutdown`) are passed on to the host.

The host's lease is short (`WARDEN_REMOTE_TTL`, 90 s by default) and a background keepalive renews it every 30 s while your local lease lives. If the laptop sleeps, crashes or loses the network, the host frees the device within that TTL.

A lease on a host can also end without a release. `warden events` records it as `host_lost`, and a `warden run` or `warden dev` holding it stops with `LEASE_LOST`:

| Reason | When |
|---|---|
| `unreachable` | three renewals in a row couldn't reach the host |
| `remote_gone` | the host no longer holds the lease |
| `host_expired` | a hosted Mac's session reached its end; `warden heartbeat` warns 10 minutes before |

To drive the device, put the app on it and use `warden ui`:

```bash
warden app ensure --lease <lease id> --json
warden ui open com.example.app
warden ui snapshot -i
```

`app ensure` builds or fetches the app here, sends it to the host once per content hash, and installs it there. `warden ui` runs its driver on the host over ssh. Verbs that run local tools (screenshots, rotation, network conditions, devtools) don't reach a host's device yet, and neither does `warden e2e`.

To watch or drive it yourself, open it in a browser tab:

```bash
warden view            # your only device lease, or: warden view <lease id>
warden view --watch    # read-only
```

The page is served on `127.0.0.1` behind a random link, and frames and input go through the same driver as `warden ui`. Click to tap, drag to swipe, type on the keyboard; Esc is the home button. Ctrl-C stops viewing and keeps the lease.

## Run a dev client on a host

```bash
warden dev ios --host mac
```

Metro and the project stay on your laptop. `warden dev --host` claims a device on the host, starts Metro here, sends and installs the dev build there, and opens one `ssh -R` so Metro answers on the host's loopback. The dev client is pointed at it, and fast refresh and devtools ride the same port. The host leases its end of the forward and frees it as soon as the ssh closes.

Output is plain (no dashboard). Ctrl-C stops Metro, closes the tunnel and releases the device here and on the host. `--udid`, `--lease`, `--install-mode`, `--hud` and `--devtools` don't apply to a host run yet, and only Expo dev clients are supported.

## Run warden commands on a host

```bash
warden --host mac perf record --json
warden host fetch mac perf <session id>
warden perf report <session id>
```

`warden --host <name> <command>` (or `warden host run <name> -- <command>`) runs a command with the host's warden and shows its output here: `perf`, `golden ls` / `ensure`, `builds ls`, `capacity` and `queue`. Perf acts only on a device you hold there; with one device on that host you don't need `--lease`. `warden host fetch` copies a perf session back into your own perf directory, so `warden perf report`, `query` and `diff` read it as if it ran here. Fetch before you release the device.

Specs don't run this way, because they would run code on the host.

A claim that can't reach the host is tried three times with the same idempotency key, so a claim that landed before the link dropped is returned rather than made twice.

## What the laptop's key can do

The grant is a forced command in the host's `~/.ssh/authorized_keys`:

```text
command="/Users/me/.local/bin/warden __host-serve --key SHA256:…",restrict,port-forwarding ssh-ed25519 AAAA… warden:<machine>:<user>
```

The key cannot open a shell. It can run `version`, `claim`, `heartbeat`, `release`, `ls`, `port` and `doctor` (all with `--json`), serve the driver of its own leased device, take an app build, hold the far end of a `warden dev --host` forward, and run the `warden host run` commands above. Selectors that would reach other people's leases are refused, and so is a lease id another owner holds. On the host, every session from one laptop is one owner, `host:<machine>`, whose leases live by heartbeat and a short TTL (90 s by default, `WARDEN_REMOTE_TTL`): a laptop that disappears frees its devices within that.

Manage grants on the host itself: `warden host grants`, `warden host revoke --key SHA256:…`.

## Security

- Key auth only, `BatchMode=yes`, never agent or X11 forwarding.
- The host key is pinned per host (`~/.warden/hosts/<name>.known_hosts`); a changed key fails with `HOST_AUTH` instead of being accepted.
- No warden-api or cloud token ever goes to the host.
- `warden host setup` never uses sudo.

## Errors

| Code | Exit | Fix |
|---|---|---|
| `HOST_UNREACHABLE` | 12 | `warden host doctor <name>`; check the network, Remote Login, the proxy or jump host |
| `HOST_AUTH` | 13 | run `warden host setup <name>` again, or re-pin a changed host key with `host add --host-key` |
| `HOST_VERSION_SKEW` | 14 | `warden host setup <name>` installs this version |
| `HOST_UNKNOWN` | 15 | `warden host ls` |
