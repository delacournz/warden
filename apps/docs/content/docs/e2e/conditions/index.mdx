A spec can put the device into a condition (offline, 3G, one host failing, a moving GPS fix, a clock two weeks ahead, a failed Face ID, a denied permission, a QR code in front of the camera) and check what the app does. Everything a test changes belongs to its lease: when the test ends, warden puts it back, so the next spec never inherits a shaped device.

```ts title="e2e/network-offline.e2e.ts"
import { expect, test } from "@delacour/warden-e2e";

test("cold start offline shows the banner, going online recovers the fetch", async ({ app, device, screen }) => {
  await device.network.set("offline"); // before the app opens: a cold start offline
  await app.open();
  await expect(screen.getByTestId("conditions-offline-banner")).toBeVisible({ timeout: 15_000 });

  await device.network.set("online");
  await expect(screen.getByTestId("conditions-offline-banner")).toBeHidden({ timeout: 15_000 });
});
```

The example app has a Conditions screen (`warden-example://conditions`) and a spec for each area in `apps/example/e2e`.

## Suite baseline: the `conditions` key

`conditions` at the top level of `warden.config.ts`, or inside a suite, is the device state every spec starts from. It is applied before the app launches and put back after each spec.

```ts title="warden.config.ts"
e2e: {
  conditions: {
    ...exampleSuite,
    include: ["{network-*,location-*,clock-*}"],
    conditions: { network: "online" },
  },
},
```

| Area | Value |
|---|---|
| `network` | `"online"`, `"offline"`, a preset or `{ latencyMs, jitterMs, downKbps, upKbps, lossPct }` |
| `location` | `{ lat, lon, altM? }` or a scenario name |
| `clock` | an ISO instant (it keeps running), `{ at, frozen? }` or `{ offset: "2d" }` |
| `permissions` | `{ location: "denied", camera: "granted", … }` |
| `locale` | a BCP 47 tag |
| `timezone` | an IANA name |
| `a11y` | `{ textSize?, boldText?, contrast?, reduceMotion? }` |
| `keyboard` | `"software"` (default) or `"hardware"` |

A suite's key replaces the top-level one for that area. A bad value fails config load. On iOS, declaring `network` or `clock` launches the app with the dylib, which is why the example runs its condition specs in a separate `conditions` suite: the other specs keep a plain launch.

```bash
warden e2e conditions --specs conditions/network,conditions/location,conditions/clock
```

The camera feed is the suite's own `camera` key, not a `conditions` key ([Camera](/docs/e2e/conditions/camera#in-a-suite)). Biometrics is not one either: enrolled devices come from `biometrics: true` ([Biometrics](/docs/e2e/conditions/biometrics#enrolled-devices-biometrics-true)).

## Timeline

```ts
const run = await device.timeline([
  { at: "0s", network: "offline" },
  { at: "5s", network: "online", location: { lat: 37.33, lon: -122.0 } },
]);
```

A timeline changes the network and the location on a schedule. `at` is an offset from now. A step sets a condition, not a flap. The returned run has the same `stop()`, `done` and `status()` as a [flap](/docs/e2e/conditions/network#flapping).

## What is undone after each spec

The end of a spec puts the device back to the suite's baseline (or the real state without one): the network, location, clock, permissions, accessibility settings, locale, timezone, battery, keyboard and camera feed. Each change a spec makes is a `condition` line in `results.jsonl`. The full list is in [What is undone on release](/docs/sims/conditions#what-is-undone-on-release).
