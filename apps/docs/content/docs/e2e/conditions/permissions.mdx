---
title: Permissions
description: Grant, deny or unset the app's privacy permissions before it launches, so a spec reaches the screen behind the prompt, or the denied path.
icon: ShieldCheck
---

`device.permissions` sets the app's privacy permissions directly, so a spec does not tap through a system prompt (iOS does not always raise one) and can test the denied path on purpose.

```ts
await device.permissions.set({ location: "denied", notifications: "granted" });
await app.open();
```

Set permissions before `app.open()`: iOS terminates a running app whose permission changes.

| Member | Does |
|---|---|
| `set({ location?, camera?, photos?, … }, { bundleId? })` | each `"granted" \| "denied" \| "unset"` (`unset` asks again). Returns `{ bundleId, applied, skipped }`; none applicable throws `E_UNSUPPORTED`. Default app: the suite's |
| `reset({ bundleId? })` | every name this test set back to the suite's value, else `"unset"` |

Names: `location` `locationAlways` `camera` `photos` `photosAdd` `contacts` `contactsLimited` `notifications` `microphone` `calendar` `reminders` `motion` `mediaLibrary` `siri`.

## Skipped names

A name comes back in `skipped` when the platform has no service for it or the app does not declare it.

- **iOS:** `camera` and `notifications` have no `simctl privacy` service and are skipped.
- **Android:** only the permissions the app's manifest declares apply; any other name is skipped with a warning.

## In a suite

```ts title="warden.config.ts"
conditions: { permissions: { location: "denied", camera: "granted" } },
```

Applied before the app launches, and put back after each spec.

## By hand

```bash
warden ui permission set location=granted camera=denied
warden ui permission status
warden ui permission reset
```

`--app <bundle>` names the app; the default is the one `warden ui open` launched. Run `permission set` before `open`. Release puts the permissions back (iOS: privacy reset; Android: permissions reset).
