Three commands from an Expo app to a passing end-to-end test on a leased simulator or emulator:

```bash
warden init --bundle-id com.example.app   # writes warden.config.ts and e2e/smoke.e2e.ts
bun add -d @delacour/warden-e2e@<version> # run the exact line init prints
warden e2e                                # leases a device, builds the app, runs the specs
```

The rest of this page walks through each one, then turns the smoke test into a real one.

## Before you start

| | iOS | Android |
|---|---|---|
| Machine | macOS with Xcode and an iOS simulator runtime | the Android SDK (`adb`, `emulator`) |
| warden | installed ([Installation](/docs/getting-started/installation)), `warden doctor` green | same |
| App | an Expo app | an Expo app |

No bun install is needed for the specs: `warden e2e` runs them with the bun built into warden.

## Or set up manually

An e2e test is a `*.e2e.ts` file that drives your app on a real simulator or emulator and asserts on what is on screen. Pick your platform once; every tab on this page follows it.

<Steps>
<Step>
### Scaffold

<Tabs groupId="platform" persist items={["iOS", "Android"]}>
<Tab value="iOS">
```bash
warden init --bundle-id com.example.app
```
</Tab>
<Tab value="Android">
```bash
warden init --platform android --bundle-id com.example.app
```
</Tab>
</Tabs>

`--bundle-id` is only needed when `app.json` has no id for the platform; it is written there. `init` writes `warden.config.ts` (one suite, `platform` set from `--platform`, default `ios`) and `e2e/smoke.e2e.ts`. Existing files are kept (`--force` overwrites), and an app that already has specs gets no smoke spec. `--dry-run` prints the plan.
</Step>
<Step>
### Install the spec package

`init` installs nothing: it prints one install line per missing package, in your project's package manager (from the lockfile; bun without one). Run the `@delacour/warden-e2e` line as printed, e.g.:

```bash
npm install -D @delacour/warden-e2e@0.16.0
```

It is pinned to the version `warden --version` prints: the spec runner refuses any other. `init` also names `expo-dev-client` when it is missing; that one is for `warden dev`, not for `warden e2e`.
</Step>
<Step>
### Add testIDs to your components

Specs read the accessibility tree. A `testID` is only exposed when the native view is `accessible`, so mark every view a spec taps or asserts on.

```tsx title="src/todo-list.tsx"
<TextInput testID="todo-input" accessible value={draft} onChangeText={setDraft} />
<Pressable testID="todo-add" accessible onPress={add}>
	<Text>Add</Text>
</Pressable>
<Text testID="todos-remaining" accessible>{`${remaining} left`}</Text>
```

A missing id is fixed here, not with retries or longer timeouts.
</Step>
<Step>
### Write a spec

`init` leaves `e2e/smoke.e2e.ts`, which only opens the app. Add one that does something:

```ts title="e2e/todos.e2e.ts"
import { expect, test } from "@delacour/warden-e2e";

test.use({ launch: "none" });

test("adding a todo updates the count", async ({ app, screen }) => {
	await app.open({ wait: { until: screen.getByTestId("todo-input") } });

	await screen.getByTestId("todo-input").fill("Write e2e specs");
	await screen.getByTestId("todo-add").tap();

	await expect(screen.getByText("Write e2e specs")).toBeVisible();
	await expect(screen.getByTestId("todos-remaining")).toHaveText("1 left");
});
```

The runner opens the app before every test and does not wait for a screen. `launch: "none"` skips that open so the test can open it and wait for the screen it names: `app.open({ wait: { until: locator } })` returns once that locator is visible, so the first tap lands.

`screen.getByTestId(id)` is the stable locator; a locator is lazy and nothing is read until you act or assert. `expect(locator)` polls until it holds. Full reference: [Write specs](/docs/e2e/specs).
</Step>
<Step>
### Run it

```bash
warden e2e
```

With one suite in the config the name is optional; the suite's `platform` picks iOS or Android. The first run of a native fingerprint builds the app, which takes minutes; later runs reuse the cache.

A green run ends like this on stderr:

```text
warden e2e: tests 2 passed · 0 failed · 0 skipped
evidence in <batchDir>
2/2 spec(s) passed — gate passed
took <total> — setup <s> · tests <t> · teardown <d>
```

Exit code `0` means every required spec passed. A project without `@delacour/warden-e2e` fails before any device is claimed.
</Step>
<Step>
### When it is red

The run lists the failed specs and tests and prints `evidence in <batchDir>`. Open `screen-at-failure.txt` there first: it is the accessibility tree at the failure, and a query that found nothing is an element that is missing or not `accessible`. [Debugging](/docs/e2e/debugging) walks through a first failure and lists every evidence file.
</Step>
</Steps>

## Run on more devices

```bash
warden e2e --count 5
```

`--count` leases that many devices and spreads the specs over them, one `bun test` process per device (the clip at the top is 37 specs on 5 simulators). Suite keys (`count`, `platform`, `app`, `metro` and the rest) are in [Suites](/docs/e2e/suites); one spec against a device you claimed yourself is [Run a spec by hand](/docs/e2e/specs#run-a-spec-by-hand).

## Let your agent write specs

Your agent drives the app with [`warden ui`](/docs/sims/ui) between `warden ui record start <name>` and `warden ui record stop`. `stop` writes `<specsDir>/<name>.e2e.ts`, lints it, merges the testIDs it used into a module and runs it once on the same device. Details: [Record specs](/docs/e2e/author-specs).

If your agent does not know warden yet, see [Set up your agent](/docs/getting-started/agent-setup). Then paste:

```text
Use warden to write an e2e spec for adding a todo in this app.
1. Claim a simulator, open the app, and record: warden ui record start add-todo --udid $UDID.
2. Drive the flow with warden ui. Target elements by testID (id=...). If snapshot -i marks an element [no-id], add testID and accessible in the component first.
3. Add one `warden ui record note "<step>"` per user-visible step, and assert the result with warden ui wait.
4. warden ui record stop. If verify fails, read screen-at-failure.txt, fix the app or undo and redo the steps, and stop again.
5. Release the device with warden ui close --release.
```
